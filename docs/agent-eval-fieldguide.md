# 第一部分 · 目的与坐标系（先建立定位）

## §1 一句话：评估到底在回答什么（以及为什么它难）

### 1.1 唯一要回答的问题

所有 agent 评估，归根到底只服务**一个问题**：

> **「我这个会犯错、还不确定的 agent，整体到底好不好？这次改动有没有让它变差？」**

记住这句。后面所有概念都只是为了回答它而存在——任何时候被绕晕，就回到这句。

### 1.2 为什么这个问题难回答（vs 传统软件测试）

转行同学最容易踩的坑：以为「评估 = 写单元测试」。两者根本区别如下——**面试官第一刀往往就砍这里**，也正是这些区别让上面那个问题难答、催生出后面一整套方法：

| 维度 | 传统软件测试 | LLM / Agent 评估 |
|---|---|---|
| 输出 | **确定**：同输入永远同输出 | **非确定**：同输入可能不同回答（即便 `temperature=0` 也会微抖）→ 催生 §7 |
| 正确性 | **精确相等**：`assert f(2)==4` | **语义正确**：「明天下午两点」≈「14:00」，判**意思**对不对 → 催生 §6 |
| 标准答案 | 唯一 | 常常**没有唯一答案** → 催生 §6 的 LLM-judge |
| 失败形态 | 抛异常 / 断言失败 | **悄悄答错**：流程跑通、格式正确，但内容是幻觉 / 调错工具 |
| 评估者 | 代码（断言） | 代码 + **模型当裁判** + 人工 |

**一句话总结**：传统测试问「程序有没有崩」，agent 评估问「这个会犯错、还不确定的系统，整体表现到底有多好、有没有变差」。

### 1.3 面试官到底想听什么

不是「你用过 LangSmith 吗」，而是这四个判断力信号（它们正好对应全景图的各层）：

1. **你知道评估要分层**（§2）——不能笼统说"我测了 agent"。
2. **你不会伪造指标**（§5）——没测的维度敢标 N/A，而不是算成 0%。
3. **你知道 LLM 有随机性，单次跑分不可信**（§7）。
4. **你能把评估接进流程当回归门禁**（§8），而不是跑一次截图。

> 🔗 **本项目锚定**：[../CLAUDE.md](../CLAUDE.md) 的「验证」一节写明——`evals/` 评估集用于「重构前后对照、防回归」，并「成功静默、只暴露失败；不靠『感觉对了』验收」。这正是信号 4 的工程化体现，面试时可直接引用。

## §2 坐标轴一 · 评在哪一层（最关键的认知框架）

这是整份教材**最该先记住**的一张图。Agent 评估从来不是一个数字，而是分层的：

```
┌─────────────────────────────────────────────────────────┐
│  系统级 / 业务级   "约成了没？用户满意吗？转化率？成本？"      │  ← 最终关心的
│      ▲                                                     │
│  端到端 / 轨迹级   "整段对话走对了吗？工具调用序列对吗？多轮  │  ← agent 真正的评估
│      ▲             状态流转对吗？"                           │
│  组件级           "这一个 prompt / 分类器 / 检索器，单看准  │  ← 最容易测、最先做
│                    不准？"                                  │
└─────────────────────────────────────────────────────────┘
```

- **组件级（component / unit）**：把 agent 拆成零件单独测——「意图分类器准不准」「检索器召回率多少」。**最容易做、最确定**，但测得好不代表整体好。
- **端到端 / 轨迹级（end-to-end / trajectory）**：给（多轮）输入让**整个 agent 真跑**，评它**走的整条路径**——调了哪些工具、顺序对不对、参数对不对、最终结果对不对。这才是「agent 评估」的核心，也最难。
- **系统级 / 业务级**：上线后用业务指标衡量——预约成功率、满意度、人工介入率、成本。通常靠**在线评估**（§3）。

> 💬 **面试怎么说**：「Agent 评估我会分三层——组件级、端到端轨迹级、系统级。最容易做的是组件级，但它测得好不代表 agent 整体好；真正能反映 agent 能力的是轨迹级（工具调用序列、多轮状态）；最终要落到业务指标。」**这句话一出口，面试官就知道你不是只会背概念。**

### 🔗 本项目锚定：我们现在卡在哪一层？

这是本项目**最重要、也最该诚实交代**的一点：

| 层次 | 本项目现状 | 证据（点开看） |
|---|---|---|
| 组件级-意图分类 | ✅ **真在评** | [run_evals.py:110-118](../evals/run_evals.py#L110) 逐条调真实 `classify_task` 比对 |
| 端到端-工具调用 | ❌ **永远 N/A** | [run_evals.py:132-137](../evals/run_evals.py#L132)：`actual_tools=None`——根本没驱动 AgentLoop |
| 端到端-轨迹/多轮 | ❌ 没做 | 用例 [cases.jsonl](../evals/cases.jsonl) 全是**单轮**输入 |
| 系统级 | ❌ 没做 | 无业务指标采集 |

也就是说：**本项目的 `evals/` 目前实质上是「意图分类器评估」，不是完整的「agent 评估」**——尽管标题用了 agent 评估。`metrics.py` 里设计好的「工具调用正确率」「槽位完整率」实跑时**恒为 N/A**，因为运行器只跑了分类器、没跑 [agent_loop.py](../harness/runtime/agent_loop.py) 这个 TAO 循环。

> ⚠️ **这是面试的关键诚实点**，不是缺点要藏，而是要主动讲清楚（见 §10 陷阱题、§11 话术）。能清楚说出「我评到了哪一层、还差哪一层」本身就是分层认知的最佳证明。

## §3 坐标轴二 · 什么时候评（离线 vs 在线）

两条腿，缺一不可。面试常问「你怎么持续保证质量」，答案就是这两者配合。

| | 离线评估（Offline / Eval set） | 在线评估（Online / Monitoring） |
|---|---|---|
| 数据 | **固定的测试用例集**（标好答案） | **生产真实流量**（采样真实对话） |
| 时机 | 改代码 / 改 prompt **之前**，CI 里跑 | **上线后**持续跑 |
| 目的 | **防回归**：新版本别比老版本差 | **抓真实问题**：线上有没有翻车、漂移 |
| 有没有标准答案 | 有（人工标注） | 多数**没有**（靠 LLM-judge / 用户反馈信号） |
| 典型指标 | 准确率、工具调用正确率、通过率 | 满意度、人工介入率、延迟、成本、异常率 |

**关键认知**：离线用例再多也覆盖不全真实分布；线上流量再真实也没有标准答案。**成熟做法是闭环**——线上发现的 bad case → 标注后**回灌进离线用例集** → 下次回归就能防住它。

### 🔗 本项目锚定

- **离线**：整个 [`evals/`](../evals/) 就是离线评估——固定 [cases.jsonl](../evals/cases.jsonl)，CI/验证闸门里跑（见 §8）。
- **在线的地基已有，但没接**：本项目有完整的**可观测层 tracer**——[tracer.py](../harness/observability/tracer.py)，在 [agent_loop.py:142-157](../harness/runtime/agent_loop.py#L142) 为每次 run 开 root span、每步开 child span，记录 thought / tool_call / observation / latency / token。**这正是「在线评估」的数据来源**：生产 trace 采样回来就能喂给评估。只是目前 tracer 用于调试观测，还没接成「从线上 trace 采样 → 标注 → 回灌离线集」的闭环。

> 💬 **面试怎么说**：「离线防回归、在线抓真实问题，两者要闭环——线上 bad case 标注后回灌离线集。我这个项目离线评估有了；在线这块我已经有 tracer 把每步 thought/tool_call/observation 都记成 span 了，数据地基在，差的是把采样和回灌闭环接起来。」

# 第二部分 · 每个格子里的三件事（往下钻）

> 在全景图任意一个「格子」里落地评估，都要依次回答三件事：**① 拿什么当标准答案（§4）→ ② 用什么指标量化（§5）→ ③ 怎么判对错（§6）**。顺序不能乱。

## §4 三件事之一 · 标准答案：评估数据集（被低估、但面试高频）

「你的评估用例从哪来、有多少、怎么保证质量」——这是必问。

### 4.1 一条用例长什么样

最小三要素：**输入 → 期望行为（标准答案）→ 元信息**。本项目的格式（[cases.jsonl](../evals/cases.jsonl)）：

```json
{"input": "我想预约明天下午两点的按摩",
 "expected_intent": "appointment",
 "expected_tools": ["find_technician", "check_availability", "create_appointment"]}
```

- `input`：用户说的话。
- `expected_intent` / `expected_tools`：**标准答案**——期望分到哪类、期望调哪些工具。
- 注意：`expected_tools` 在本项目里是**前瞻注解**（[cases.jsonl 注释](../evals/cases.jsonl) 第 4 行写明「当前不计分」），因为运行器还没驱动 loop。

### 4.2 数据集的几个必答考点

| 考点 | 要点 | 本项目现状（诚实版） |
|---|---|---|
| **规模** | 几条没统计意义，通常要几百~几千条 | ⚠️ 只 **20 条**（[cases.jsonl](../evals/cases.jsonl)：预约6/查询5/支付3/统计3/其他3） |
| **真实分布** | 用例要像真实流量，别全是简单句 | ⚠️ 全是**手写合成、单轮**，不代表线上分布 |
| **标注质量** | 谁标的、标得对不对、多人标一致吗 | 单人手写，无标注溯源 |
| **held-out（留出集）** | 调 prompt 的集 ≠ 最终验收的集，否则**过拟合** | ❌ 没有切分，有调 prompt 拟合用例的风险 |
| **版本化** | 用例集要像代码一样进 git、可追溯 | ✅ `cases.jsonl` 进了 git |
| **闭环来源** | 线上 bad case 要能回灌 | ❌ 还没接（见 §3） |

### 4.3 一个值得讲的工程细节：加载即校验

> 🔗 [run_evals.py:42-66](../evals/run_evals.py#L42) `load_cases`

本项目读用例时做了两件「数据卫生」的事，面试可当亮点：
1. **坏 JSON 不静默跳过**：解析失败时**报出行号再 re-raise**（[:54](../evals/run_evals.py#L54)），让坏数据立刻可见，而不是悄悄漏测。
2. **标签合法性校验**：`expected_intent` 不在 5 类白名单里直接 `SystemExit(2)`（[:58](../evals/run_evals.py#L58)），防手滑 typo 把用例写废还浑然不觉。

> 💬 **面试怎么说**：「数据集我关注规模、真实分布、标注质量、有没有 held-out 防过拟合，以及能不能把线上 bad case 回灌。我这个项目用例还小、是合成的，这是它当前最大的局限；但加载时做了行号报错和标签白名单校验，保证用例本身不带病。」

## §5 三件事之二 · 指标体系（本项目最有料的一节）

指标 = 把「表现好不好」量化成数字。不同层次用不同指标。

### 5.1 分类 / 抽取类指标

最基础。**准确率（accuracy）** = 答对数 / 总数。更细可看**精确率 / 召回率 / F1**（类别不均衡时准确率会骗人，要看 F1）。

> 🔗 本项目 [metrics.py:53-62](../evals/metrics.py#L53) `intent_accuracy`：`actual_intent == expected_intent` 的占比。

### 5.2 工具调用正确率（agent 特有）

Agent 评估的核心之一。但「正确」有**三个不同严格度**，面试可层层递进讲：

| 严格度 | 看什么 | 难度 |
|---|---|---|
| 名字集合 | 调了哪些工具（不看顺序、不看参数） | 最松 |
| **参数级** | 工具 + 参数都对（`create_appointment(time=14:00)` 的 time 对不对） | 中 |
| 序列级 | 工具的**调用顺序**也对 | 最严 |

> 🔗 本项目 [metrics.py:65-85](../evals/metrics.py#L65) `tool_call_correctness`：用 **`set` 比较**（[:83](../evals/metrics.py#L83)）——只看「调了哪些工具」，**顺序无关、不查参数**，属最松的「名字集合」级。
> ⚠️ 且如 §2 所述，本指标**实跑恒为 N/A**——因为 `actual_tools` 从没被填（[run_evals.py:135](../evals/run_evals.py#L135)），运行器没驱动 loop。

> 💬 **面试怎么说**：「工具调用正确性有三档——名字集合、参数级、序列级。我项目里实现的是最松的集合比较，顺序和参数都没查；而且因为运行器还没接 AgentLoop，这个指标目前其实是 N/A。要做严，得真跑 loop 拿到 actual_tools，并加参数级比对。」

### 5.3 槽位抽取完整率 + 一个统计细节：宏平均 vs 微平均

> 🔗 本项目 [metrics.py:88-115](../evals/metrics.py#L88) `slot_completeness`

「槽位」= 从话里抽出的结构化字段（时间、技师、时长…）。完整率 = 期望槽位里被正确填出的比例。

本项目用的是**宏平均（macro-average）**（[:102 注释](../evals/metrics.py#L102)）：**先算每条用例的命中比例，再跨用例求平均**，每条用例**等权**。对比：
- **宏平均**：每条用例权重一样 → 不会被「槽位特别多的那条」带偏。
- **微平均（micro）**：把所有槽位汇总成一个大分母 → 槽位多的用例影响大。

> 💬 **面试怎么说**：「指标聚合要分清宏平均和微平均——我项目槽位用的是宏平均，每条用例等权，避免被槽位多的用例带偏。类别不均衡时这个选择会显著影响结论。」**这是个能立刻显出统计素养的小点。**

### 5.4 ⭐ 最值钱的设计：缺数据显式标 N/A，不伪造分母

> 🔗 本项目 [metrics.py:65-81](../evals/metrics.py#L65)、贯穿四个指标

这是**本项目最该拿出来讲的一处判断力**。四个指标都遵循同一范式：

```python
# metrics.py:72 —— 只把「真正测过这维度」的样本纳入分母
eligible = [r for r in results if r.expected_tools is not None and r.actual_tools is not None]
if not eligible:
    return Metric("工具调用正确率", na=True,           # 显式标 N/A，附原因
                  note="本次运行未捕获实际工具调用（需端到端执行 AgentLoop）")
```

**为什么这是好设计**：假设只跑了分类器、没驱动 loop，`actual_tools` 全空。
- ❌ 错误做法：把没测的算进分母 → 得出「工具调用正确率 0%」→ **误导人以为工具全调错了**。
- ✅ 本项目做法：显式标 **N/A 并写明原因** → 读者一眼知道「不是 0 分，是这次没测」。

报告渲染也贯彻了这点——[metrics.py:155-157](../evals/metrics.py#L155) 把 N/A 连同原因一起打出来，不悄悄省略。

> 💬 **面试怎么说**（强烈建议背）：「我最在意指标的诚实性——分母只纳入真正测过的样本，没测的维度显式标 N/A 并写明原因，绝不伪造成 0% 或 100%。因为一个虚假的 0% 会让人以为系统全错，比没有数字更有害。」**这句话能直接把你和「只会跑个准确率」的候选人区分开。**

### 5.5 RAG 评估专题（本项目有 RAG，必讲）

本项目知识查询走的是 **RAG（SQLite + FAISS 向量检索）**——[knowledge.py:18](../harness/tools/knowledge.py#L18) 的 `search_knowledge` 工具薄封装了 [services/knowledge_service.py](../services/knowledge_service.py)，embedding 在 [services/text_embedding.py](../services/text_embedding.py)。RAG 系统的评估**分两段**，面试高频：

**① 检索段（retrieval）**——找回来的文档对不对：
- **召回率 Recall@k**：该找的相关文档，前 k 个里找回了几成。
- **精确率 Precision@k**：找回的前 k 个里，有几成是真相关。
- **MRR（平均倒数排名）**：第一个相关文档排在第几位（越靠前越好）。

**② 生成段（generation）——RAG 三元组**（业界经典，TruLens/Ragas 都用）：

| 指标 | 问的问题 | 防的是 |
|---|---|---|
| **Context Relevance（上下文相关性）** | 检索回来的内容和问题相关吗 | 检索跑偏 |
| **Faithfulness / Groundedness（忠实度）** | 回答是不是**有检索内容支撑**、没瞎编 | **幻觉** |
| **Answer Relevance（答案相关性）** | 回答真的回应了用户的问题吗 | 答非所问 |

> 🔗 **本项目现状**：RAG 系统在（检索 + 生成俱全），但 **`evals/` 完全没有评 RAG 质量**——既没测检索 Recall@k，也没测三元组。这是本项目一块明显空白，也是很好的「我下一步会做」素材。

> 💬 **面试怎么说**：「RAG 要分检索段和生成段评——检索看 Recall@k / MRR，生成看 RAG 三元组：上下文相关性、忠实度（防幻觉）、答案相关性。我项目里有 SQLite+FAISS 的 RAG，但目前评估集还没覆盖 RAG 质量，这是我会优先补的一块。」

### 5.6 成本与延迟

生产必看：**延迟**（用户等多久）、**token / 费用**（一次对话烧多少钱）。

> 🔗 本项目只测了**分类器单次调用的延迟**——[run_evals.py:113-118](../evals/run_evals.py#L113) 用 `time.perf_counter()` 计时，[metrics.py:118-132](../evals/metrics.py#L118) `latency_summary` 汇总 **avg / p50 / max**（注意它给了 p50/max 而不只是均值，这点是对的——延迟要看尾部）。
> ⚠️ 但这是**分类器一次调用**的延迟，不是 agent 全链路延迟；**token / 费用完全没测**。

> 💬 **面试怎么说**：「延迟我会看 p50 和 p99 而不只是均值，因为用户体验由尾部决定。我项目测了延迟的 avg/p50/max，但只是分类器单次调用，agent 全链路延迟和 token 成本还没纳入。」

## §6 三件事之三 · 怎么判对错：客观比对 vs LLM-as-judge

§4 有了标准答案、§5 选好了指标，最后一步是**怎么判一条回答到底对不对**。两类判法：

- **客观比对**：能用 `==` / `set` / 数值比的（意图对不对、调了哪些工具）——本项目目前**全部**属于这类。
- **LLM-as-judge（模型当裁判）**：用于**没有唯一标准答案**的主观维度。

### 6.1 为什么需要 LLM-as-judge

§1.2 说过：很多输出**没有唯一标准答案**（一句回话是否「礼貌、有帮助、相关」无法用 `==` 判）。这时用**另一个 LLM 当裁判**给回答打分，是业界主流解法。

两种打分方式：
- **Pointwise（逐条打分）**：给单个回答打 1–5 分 / 判合格不合格。
- **Pairwise（两两对比）**：给「回答 A vs 回答 B 哪个好」——**通常比逐条打分更稳**（人和模型都更擅长比较而非绝对评分）。

### 6.2 它的坑（面试加分点）

LLM 裁判**自己也有偏差**，知道这些 = 懂行：
- **位置偏差**：倾向选**靠前**的那个 → 对策：A/B 位置互换跑两次。
- **长度偏差**：倾向选**更长**的回答。
- **自我偏好**：模型倾向给**自己同款模型**的输出打高分。
- **校准**：裁判打的分要**和人工标注对齐**过（抽一批人工标，验证裁判和人一致率），否则裁判本身不可信——这条直接通向 §7。

> 🔗 **本项目现状**：**完全没有 LLM-as-judge**。本项目所有指标都是「能用 `==` / `set` 判」的客观指标，没有评「回复质量」这类主观维度。**这是本项目最大的能力缺口，也是最好讲的「下一步」。**

> 💬 **面试怎么说**：「对没有唯一答案的回复质量，我会用 LLM-as-judge，优先 pairwise 对比、且会做位置互换消除位置偏差，再抽样和人工标注校准裁判本身。我现在这个项目还只有客观指标（意图、工具集合），回复质量的 judge 是我会加的第一块。」

# 第三部分 · 让评估本身可信（横切关注点）

## §7 评估的可信度：别拿一个会骗人的数字下结论

前面 §4-§6 产出了指标，但**指标本身得可信**，否则是自欺。这一节横切所有格子，把分散在前面的「可信度」要点收口成一处。

### 7.1 治非确定性（核心）

§1.2 的根本难点：**同输入不同输出**。处理不好，跑分就是「今天 82% 明天 79%」的噪声。

- **多次采样取平均**：每条用例跑 N 次，看平均和**方差**，而不是单次。
- **pass@k**：跑 k 次，只要有一次对就算过（适合代码生成等「能对一次就行」的任务）。
- **置信区间**：20 条用例的 85% 和 200 条的 85% 可信度天差地别——样本小要给出不确定性。
- **`temperature=0` 不等于确定**：能降低随机性，但 provider 侧仍可能微抖，不能当成"锁死"。

### 7.2 另两条可信度防线（已在前文，这里收口）

- **裁判可信**：LLM-judge 要和人工标注校准、警惕三种偏差——详见 §6.2。
- **数据可信**：规模、真实分布、held-out 防过拟合——详见 §4.2。

> 🔗 **本项目现状（诚实）**：[../evals/README.md:54](../evals/README.md) 明确自承——意图准确率是「**一次性运行记录、非永久基线**，且**非确定性**（即便 temperature=0 也可能微抖）」。本项目分类器确实设了 `temperature=0`（[run_evals.py:101](../evals/run_evals.py#L101)）求确定性，但**没有多次采样 / 方差 / 置信区间**——只跑一次。

> 💬 **面试怎么说**：「LLM 评估最大的陷阱是拿单次跑分当结论。我会多次采样看均值和方差，小样本给置信区间。temperature=0 能降随机但不等于确定。我项目目前是单次跑、且只有 20 条用例，所以那个准确率只能当一次性记录、不能当稳定基线——这一点我在 README 里写明了。」

# 第四部分 · 让评估发挥作用（落地）

## §8 落地之一 · 回归门禁与 CI

评估的价值不在「跑一次截图」，而在**变成关卡**：新版本不达标就**别想合并/发布**。

要素：
1. **持久化基线**：把上一版的分数存下来。
2. **阈值 / 门禁**：新版本低于基线（或低于绝对阈值）就**让 CI 失败**。
3. **退出码语义**：脚本要用退出码告诉 CI「过 / 没过 / 没真跑」。

> 🔗 本项目锚定：
> - **退出码语义做得不错**——[run_evals.py](../evals/run_evals.py) 用 `0`=正常跑完、`1`=文件缺失、`2`=用例非法或**无 key 优雅降级**（[:171-179](../evals/run_evals.py#L171)）。CI 能据此区分「真跑过」和「跳过了」。
> - **优雅降级**：没配 API key 不崩，退而打印用例清单 + 提示，非零退出（[:169-179](../evals/run_evals.py#L169)）。
> - **门禁的「位置」已规划好**：[../CLAUDE.md](../CLAUDE.md) 写明开发流程有**两道闸门**，闸门 2（验证）就是「实现后跑 `uv run pytest`（及 `evals/`），绿了才归档」。
> - ⚠️ **但「持久化基线 + 阈值阻断」还没落地**：[../evals/README.md:62](../evals/README.md) 把「把跑 evals 接入 `/phase` 的验证闸门」列为 **TODO**。目前是人工跑、人工看，没有自动比对基线后阻断。

> 💬 **面试怎么说**：「评估要接进 CI 当回归门禁才有意义——存基线、设阈值、不达标就让 CI 失败。我项目的退出码语义和优雅降级都做了（区分真跑过/跳过/降级），开发流程里也规划了验证闸门；还差的是把基线持久化和阈值阻断自动化，现在还是人工跑人工看。」

# 第五部分 · 面试实战

## §10 高频面试问答（背熟）

> 答案都尽量「**概念 + 本项目举例**」，这样既显理论又显落地。

**Q1. 你怎么评估一个 agent 的性能？**
> 分三层：组件级（单个分类器/检索器准不准）、端到端轨迹级（工具调用序列、多轮状态对不对）、系统级（业务指标）。再分离线（防回归）和在线（抓真实问题）两条腿，且要闭环——线上 bad case 回灌离线集。我做过的项目里实现了离线 + 组件级（意图分类），轨迹级和在线还在路上。

**Q2. LLM 输出不确定，你怎么保证评估可信？**
> 不拿单次跑分当结论：多次采样看均值和**方差**，小样本给置信区间，必要时用 pass@k。temperature=0 能降随机但不等于锁死。我项目目前是单次跑 + 20 条用例，所以我明确把那个准确率当「一次性记录、非稳定基线」，没敢当结论——这点我写进 README 了。

**Q3.（陷阱题）那你这个项目的工具调用准确率是多少？**
> 老实说**目前是 N/A**——因为我的运行器只驱动了意图分类器、还没驱动完整的 AgentLoop，拿不到实际调用的工具（actual_tools 是空的）。我**特意让它显式标 N/A 并写明原因**，而不是算成 0%——因为一个虚假的 0% 会误导人以为工具全调错了。要让它出真数，得让运行器真跑 loop、并加参数级比对。**（这题答好了反而是加分——见 §5.4 和 §11。）**

**Q4. 没有标准答案的回复质量怎么评？**
> 用 LLM-as-judge，优先 pairwise 对比并做位置互换消除位置偏差，再抽样和人工标注校准裁判本身。要警惕位置/长度/自我偏好三种偏差。我项目目前只有客观指标，judge 是我会加的第一块。

**Q5. RAG 系统怎么评？**
> 分检索段和生成段。检索看 Recall@k、Precision@k、MRR；生成看 RAG 三元组——上下文相关性、忠实度（防幻觉）、答案相关性。我项目有 SQLite+FAISS 的 RAG，但评估集还没覆盖 RAG 质量，是我下一步。

**Q6. 评估怎么接进开发流程？**
> 接成 CI 回归门禁：存基线、设阈值、不达标 CI 失败，用退出码区分通过/失败/跳过。我项目的退出码语义和无 key 优雅降级都做了，开发流程也规划了验证闸门，差的是基线持久化和阈值自动阻断。

**Q7. 你的评估用例从哪来、够不够？**
> 我项目是手写合成的 20 条，覆盖 5 类意图。坦白说规模小、是合成的、单轮，不代表真实分布——这是它当前最大局限。理想做法是从生产 trace 采样 + 人工标注，做几百上千条，并切出 held-out 防过拟合。

**Q8. 准确率和 F1 你会选哪个？**
> 看类别均衡。均衡时准确率够用；不均衡时准确率会骗人（全猜多数类也能高分），要看精确率/召回率/F1。聚合还要分宏平均（每条等权）和微平均——我项目槽位用的是宏平均，避免被槽位多的用例带偏。

**Q9. 你用过哪些评估框架？**
> （见 §9 话术——诚实说自研轻量框架 + 了解 LangSmith/LangFuse/Ragas/DeepEval 的定位 + 本项目的自然延伸。）

**Q10. 你评估设计里最得意的一点是什么？**
> 指标的诚实性：分母只纳入真正测过的样本，没测的显式标 N/A 写明原因，绝不伪造 0%/100%；以及把指标算成纯函数、和「跑模型」解耦，所以评估逻辑本身能离线确定性单测。我觉得评估代码本身也得是可信、可测的。

**Q11. 离线评估和在线监控有什么区别？**
> 离线是上线前用固定标注用例防回归；在线是上线后采样真实流量抓问题，多数没有标准答案，要靠 LLM-judge 和用户反馈信号。两者闭环——线上 bad case 回灌离线集。我项目离线有了，在线有 tracer 数据地基但没接闭环。

**Q12. 你会怎么评估一个 agent 的工具调用？**
> 三个严格度递进：名字集合（调对工具没）、参数级（参数对不对）、序列级（顺序对不对）。我项目实现的是集合比较，且因为还没驱动 loop 目前是 N/A；要做严得真跑端到端拿 actual_tools，再加参数比对。

## §11 诚实话术：怎么框定本项目不被戳破

转行同学最大的风险是**无意中吹过头**（说「我做了 agent 性能评估系统」），被追问就崩。**把下面这套框定背下来，把劣势变成判断力的展示。**

**❌ 别这样说**：「我做了一套 agent 性能评估系统。」
→ 一问「工具调用准确率多少」就露馅（N/A），一看代码发现只评了分类器。

**✅ 这样说**：
> 「我搭了一个**评估 harness 框架**，核心有两点判断力：一是**指标完整性**——缺数据显式标 N/A、不伪造分母；二是**计算与执行解耦**——指标是纯函数、不触网，所以评估逻辑本身能离线确定性单测。目前它**接入并评估了意图分类这一个环节**；工具调用和端到端轨迹的指标**已经设计好、有单测覆盖，但还没接到真实 AgentLoop 执行**，所以那两个指标现在是 N/A。下一步就是让运行器真跑 loop、加 LLM-judge 评回复质量、接 Ragas 评 RAG。」

**这套话术的三个好处**：
1. **不吹牛**：明说「只评到分类器这一层」，经得起看代码。
2. **显认知**：用「分层」「N/A 不伪造」「解耦可测」三个词，证明你懂的是方法论而非堆功能。
3. **有路线**：能说清「下一步做什么」，显出你知道完整的 agent 评估长什么样。

**记住 §1.1 那句话**：面试官考的是判断力。一个能清楚说出「我评到了哪层、还差哪层、为什么这么设计」的转行新人，比一个声称「全做了」却答不上细节的人可信得多。

## §13 改造路线图：从「分类器评估」→「完整 agent 评估」

下面 8 项改造按**依赖与 ROI 排序**。每项标了：目标 / 改哪里（锚定真实代码）/ 产出 / 工作量（S·M·L）。

> ⚠️ **这些都是代码变更**——按本项目的 OpenSpec SDD 规矩，每项应各走**一个 OpenSpec change**（`/opsx:propose` → 人审 → `/opsx:apply` → 验证 → 归档），不要直接散改源码（见 [../CLAUDE.md](../CLAUDE.md)）。

```
   改造1 接 AgentLoop  ──┬──▶ 改造2 工具调用做严
   (地基/解锁最多)        ├──▶ 改造3 治非确定性
                         └──▶ 改造5 RAG 评估
   改造4 LLM-judge ───────────▶ (回复质量, 独立可并行)
   改造1+2 出真数 ────────────▶ 改造6 CI 门禁 ──▶ 改造7 在线闭环
   改造8 数据集扩充 ──────────▶ (贯穿始终, 持续做)
```

### ⭐ 改造 1 · 让 run_evals 真跑 AgentLoop（最高优先级，解锁最多）

- **目标**：把 evals 从「只跑分类器」升级为「真跑端到端」，让 `actual_tools` / `actual_slots` 出真数——**这是把项目从「分类器评估」变成「agent 评估」的关键一步**。
- **改哪里**：在 [run_evals.py](../evals/run_evals.py) 的 `run_baseline` 里，除 `classify_task` 外，再构造一个 `AgentLoop`——用 [`build_default_registry()`](../harness/tools/registry.py#L123) + [`create_chat_model()`](../evals/run_evals.py#L96)，并注册 `on_tool_call` 钩子（[`AgentLoop` 已预留](../harness/runtime/agent_loop.py#L76)，每次工具调用都会回调）把工具名收集进一个 per-case 列表，跑完 loop 后填进 `EvalResult.actual_tools`。
- **⚠️ 一个非踩不可的坑**：生产的**主 loop 只含 `delegate` 一个工具**（[chat_handler.py:50](../api/chat_handler.py#L50)），在主 loop 上挂钩子只会看到 `"delegate"`，看不到 `find_technician` 等真实领域工具（它们在子 Agent 的工具子集里跑）。所以评工具调用要么**用 `build_default_registry()` 直接驱动一个含全量工具的 loop**（最简单），要么**同时 hook 子 Agent 的 loop**。这点想清楚，面试讲出来就是深度。
- **产出**：`tool_call_correctness` / `slot_completeness` 从「永远 N/A」→ **真实数字**。§12 表里两行 ❌ 直接转 ✅。
- **工作量**：M

### 改造 2 · 工具调用做严（参数级 + 序列级）

- **目标**：从最松的「名字集合」升到「参数对不对、顺序对不对」（见 §5.2 三档）。
- **改哪里**：扩展 [metrics.py 的 `tool_call_correctness`](../evals/metrics.py#L65)（现在是 `set` 比较）；[cases.jsonl](../evals/cases.jsonl) 给用例补 `expected_tool_args`（及需要时的顺序）。
- **产出**：工具调用指标从「调对了没」升到「调得对不对」。**依赖改造 1**（先有 actual_tools 才谈得上比参数）。
- **工作量**：S–M

### 改造 3 · 治非确定性（多次采样 + 方差/置信区间）

- **目标**：让跑分从「单次噪声」变成「可信结论」（见 §7）。
- **改哪里**：[run_evals.py](../evals/run_evals.py) 对每条用例跑 N 次；[metrics.py](../evals/metrics.py) 增加方差 / 置信区间 / pass@k 的计算。
- **产出**：报告能给出「85% ± x%（n 次）」而非一个孤零零的数。
- **工作量**：M

### 改造 4 · 接 LLM-as-judge（评回复质量）

- **目标**：评「没有唯一答案」的回复质量（见 §6）——本项目最大的能力缺口。
- **改哪里**：新增一个 judge 模块（用 `create_chat_model` 当裁判，**pairwise + 位置互换**消除位置偏差）；[metrics.py](../evals/metrics.py) 增加 `response_quality` 指标；[cases.jsonl](../evals/cases.jsonl) 给需要评质量的用例补 reference answer 或评分 rubric。
- **产出**：从「只有客观指标」扩展到「主观质量也能量化」。可与改造 1 **并行**（不依赖工具捕获）。
- **工作量**：L

### 改造 5 · RAG 评估（检索 + 生成）

- **目标**：补上 §5.5 的 RAG 评估空白。
- **改哪里**：对 [knowledge_service.py](../services/knowledge_service.py) 的检索结果评 **Recall@k / MRR**（需给 RAG 用例标注「哪些文档才算相关」）；对生成评 **RAG 三元组**（复用改造 4 的 judge）。
- **产出**：RAG 这条线（项目里实打实存在的能力）终于被评上。**依赖改造 4 的 judge**（三元组靠 judge 打分）。
- **工作量**：L

### 改造 6 · CI 回归门禁（基线持久化 + 阈值阻断）

- **目标**：让评估从「人工跑人工看」变成「自动拦不达标」（见 §8）。
- **改哪里**：把每次跑分结果**持久化成基线**（存 JSON）；[run_evals.py](../evals/run_evals.py) 跑完**比对基线**，回归（低于基线/阈值）就非零退出；最后把「跑 evals」接进 `/phase` 的**验证闸门 2**（[README:62 的 TODO](../evals/README.md)）。
- **产出**：兑现 [CLAUDE.md](../CLAUDE.md) 里「闸门 2 跑 evals 防回归」的承诺。**依赖改造 1+2 出真数**（否则门禁守的是 N/A）。
- **工作量**：M

### 改造 7 · 在线评估闭环（trace 采样 → 标注 → 回灌）

- **目标**：把 §3 的「在线」那条腿接起来。
- **改哪里**：用 [tracer 的 exporter](../harness/observability/exporter.py) 采样生产 trace → 人工/半自动标注 bad case → **回灌进 [cases.jsonl](../evals/cases.jsonl)**，形成「线上发现问题 → 离线防住它」的闭环。
- **产出**：离线 + 在线双腿齐全。**依赖改造 6**（有了门禁，回灌才有意义）。
- **工作量**：L

### 改造 8 · 数据集扩充（贯穿始终）

- **目标**：解决 §4 的「20 条、合成、单轮」局限。
- **改哪里**：[cases.jsonl](../evals/cases.jsonl) 从 20 条扩到几百条；引入**多轮对话**用例（配合改造 1 的端到端）；从真实流量采样（配合改造 7）；切出 **held-out** 集防过拟合。
- **产出**：让所有指标都有统计意义。**不是一次性任务，是持续投入**。
- **工作量**：持续

### 🎯 如果只做一件事

做 **改造 1**。理由：① 它把项目最尴尬的「工具调用永远 N/A」直接变成真数字；② 它是改造 2/5/6 的前置地基；③ 它把项目的定性从「分类器评估」正式抬到「agent 评估」。**一步解锁最多。**

> 💬 **面试怎么说**（"你下一步会怎么改进"）：「最高优先级是让评估真跑 AgentLoop——现在工具调用指标是 N/A，就是因为运行器只跑了分类器。接上之后工具调用、槽位就有真数了。这里有个坑：生产主 loop 只含 delegate，得用全量工具的 registry 直接驱动、或 hook 子 Agent 才抓得到真实工具。之后我会加多次采样治非确定性、接 LLM-judge 评回复质量、再把评估接进 CI 当回归门禁。」
