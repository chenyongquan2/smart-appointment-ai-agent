# 第一部分 · 目的与坐标系（先建立定位）

## §1 一句话：评估到底在回答什么（以及为什么它难）

### 1.1 唯一要回答的问题

所有 agent 评估，归根到底只服务**一个问题**：

> **「我这个会犯错、还不确定的 agent，整体到底好不好？这次改动有没有让它变差？」**

记住这句。后面所有概念都只是为了回答它而存在——任何时候被绕晕，就回到这句。

### 1.2 为什么这个问题难回答（vs 传统软件测试）

转行同学最容易踩的坑：以为「评估 = 写单元测试」。两者根本区别如下——**面试官第一刀往往就砍这里**，也正是这些区别让上面那个问题难答、催生出后面一整套方法：

| 维度 | 传统软件测试 | LLM / Agent 评估 |
|---|---|---|
| 输出 | **确定**：同输入永远同输出 | **非确定**：同输入可能不同回答（即便 `temperature=0` 也会微抖）→ 催生 §7 |
| 正确性 | **精确相等**：`assert f(2)==4` | **语义正确**：「明天下午两点」≈「14:00」，判**意思**对不对 → 催生 §6 |
| 标准答案 | 唯一 | 常常**没有唯一答案** → 催生 §6 的 LLM-judge |
| 失败形态 | 抛异常 / 断言失败 | **悄悄答错**：流程跑通、格式正确，但内容是幻觉 / 调错工具 |
| 评估者 | 代码（断言） | 代码 + **模型当裁判** + 人工 |

**一句话总结**：传统测试问「程序有没有崩」，agent 评估问「这个会犯错、还不确定的系统，整体表现到底有多好、有没有变差」。

### 1.3 面试官到底想听什么

不是「你用过 LangSmith 吗」，而是这四个判断力信号（它们正好对应全景图的各层）：

1. **你知道评估要分层**（§2）——不能笼统说"我测了 agent"。
2. **你不会伪造指标**（§5）——没测的维度敢标 N/A，而不是算成 0%。
3. **你知道 LLM 有随机性，单次跑分不可信**（§7）。
4. **你能把评估接进流程当回归门禁**（§8），而不是跑一次截图。

> 🔗 **本项目锚定**：[../CLAUDE.md](../CLAUDE.md) 的「验证」一节写明——`evals/` 评估集用于「重构前后对照、防回归」，并「成功静默、只暴露失败；不靠『感觉对了』验收」。这正是信号 4 的工程化体现，面试时可直接引用。

## §2 坐标轴一 · 评在哪一层（最关键的认知框架）

这是整份教材**最该先记住**的一张图。Agent 评估从来不是一个数字，而是分层的：

```
┌─────────────────────────────────────────────────────────┐
│  系统级 / 业务级   "约成了没？用户满意吗？转化率？成本？"      │  ← 最终关心的
│      ▲                                                     │
│  端到端 / 轨迹级   "整段对话走对了吗？工具调用序列对吗？多轮  │  ← agent 真正的评估
│      ▲             状态流转对吗？"                           │
│  组件级           "这一个 prompt / 分类器 / 检索器，单看准  │  ← 最容易测、最先做
│                    不准？"                                  │
└─────────────────────────────────────────────────────────┘
```

- **组件级（component / unit）**：把 agent 拆成零件单独测——「意图分类器准不准」「检索器召回率多少」。**最容易做、最确定**，但测得好不代表整体好。
- **端到端 / 轨迹级（end-to-end / trajectory）**：给（多轮）输入让**整个 agent 真跑**，评它**走的整条路径**——调了哪些工具、顺序对不对、参数对不对、最终结果对不对。这才是「agent 评估」的核心，也最难。
- **系统级 / 业务级**：上线后用业务指标衡量——预约成功率、满意度、人工介入率、成本。通常靠**在线评估**（§3）。

> 💬 **面试怎么说**：「Agent 评估我会分三层——组件级、端到端轨迹级、系统级。最容易做的是组件级，但它测得好不代表 agent 整体好；真正能反映 agent 能力的是轨迹级（工具调用序列、多轮状态）；最终要落到业务指标。」**这句话一出口，面试官就知道你不是只会背概念。**

## §3 坐标轴二 · 什么时候评（离线 vs 在线）

两条腿，缺一不可。面试常问「你怎么持续保证质量」，答案就是这两者配合。

| | 离线评估（Offline / Eval set） | 在线评估（Online / Monitoring） |
|---|---|---|
| 数据 | **固定的测试用例集**（标好答案） | **生产真实流量**（采样真实对话） |
| 时机 | 改代码 / 改 prompt **之前**，CI 里跑 | **上线后**持续跑 |
| 目的 | **防回归**：新版本别比老版本差 | **抓真实问题**：线上有没有翻车、漂移 |
| 有没有标准答案 | 有（人工标注） | 多数**没有**（靠 LLM-judge / 用户反馈信号） |
| 典型指标 | 准确率、工具调用正确率、通过率 | 满意度、人工介入率、延迟、成本、异常率 |

**关键认知**：离线用例再多也覆盖不全真实分布；线上流量再真实也没有标准答案。**成熟做法是闭环**——线上发现的 bad case → 标注后**回灌进离线用例集** → 下次回归就能防住它。

### 🔗 本项目锚定

- **离线**：整个 [`evals/`](../evals/) 就是离线评估——固定 [cases.jsonl](../evals/cases.jsonl)，CI/验证闸门里跑（见 §8）。
- **在线闭环已接通（改造 7，2026-07-01 核实）**：本项目有完整的**可观测层 tracer**——[tracer.py](../harness/observability/tracer.py)，生产入口的 `AgentLoop`（[chat_handler.py](../api/chat_handler.py)）已经接上 `Tracer + FileSpanExporter`，真实对话的 span 落盘到 `evals/traces/*.jsonl`；[`evals/triage.py`](../evals/triage.py) 再做半自动甄别（`guardrail_exhausted`/`spin_detected`/`tool_failure`/`max_steps_reached` 等失控信号）产标注草稿，人审填真值后回灌进 `cases.jsonl`（`source=online`，不自动重定基线）。「产 trace → 采样 → 标注 → 回灌」这条闭环**机制上是真的**。
- ⚠️ **诚实边界**：本项目没有真实线上用户流量，这里的「生产 trace」实际是开发/手动对话产出的——机制齐全，但「在线」目前是**模拟**，不是真正意义上的生产监控。

> 💬 **面试怎么说**：「离线防回归、在线抓真实问题，两者要闭环——线上 bad case 标注后回灌离线集。我这个项目两条腿都有：离线评估集 + CI 门禁；在线这边把 trace 落盘、半自动甄别失控信号、人审回灌都接通了。诚实说的是我没有真实线上流量，所以『在线』目前是拿开发对话模拟的，机制是完整的，缺的是真实流量本身。」

# 第二部分 · 每个格子里的三件事（往下钻）

> 在全景图任意一个「格子」里落地评估，都要依次回答三件事：**① 拿什么当标准答案（§4）→ ② 用什么指标量化（§5）→ ③ 怎么判对错（§6）**。顺序不能乱。

## §4 三件事之一 · 标准答案：评估数据集（被低估、但面试高频）

「你的评估用例从哪来、有多少、怎么保证质量」——这是必问。

### 4.1 一条用例长什么样

最小三要素：**输入 → 期望行为（标准答案）→ 元信息**。本项目的格式（[cases.jsonl](../evals/cases.jsonl)）：

```json
{"input": "我想预约明天下午两点的按摩",
 "expected_intent": "appointment",
 "expected_tools": ["find_technician", "check_availability", "create_appointment"]}
```

- `input`：用户说的话（或 `turns`：多轮有序话语列表，与 `input` 互斥，见改造 8 切片 2）。
- `expected_intent` / `expected_tools`：**标准答案**——期望分到哪类、期望调哪些工具。
- ⚠️ **本节曾写「`expected_tools` 当前不计分」**，那是改造 1 之前的状态。**自改造 1 起 `expected_tools` 已真实计分**——运行器真驱动 AgentLoop 采集 `actual_tools`，改造 2 又把比对从「名字集合」升到参数级/序列级（见 §5.2）。

### 4.2 数据集的几个必答考点

| 考点 | 要点 | 本项目现状（诚实版，2026-07-01 核实） |
|---|---|---|
| **规模** | 几条没统计意义，通常要几百~几千条 | ⚠️ **35 条**（[cases.jsonl](../evals/cases.jsonl)：预约20/查询6/支付3/统计3/其他3，含 6 条多轮）——比几百~几千条的门槛仍差一个数量级 |
| **真实分布** | 用例要像真实流量，别全是简单句 | ⚠️ 绝大多数是**手写合成**；改造 7 上线闭环已能从（模拟的）生产 trace 回灌 `source=online` 用例，但目前占比很小 |
| **标注质量** | 谁标的、标得对不对、多人标一致吗 | 单人手写/回灌人审，无多人交叉校验、无标注溯源 |
| **held-out（留出集）** | 调 prompt 的集 ≠ 最终验收的集，否则**过拟合** | ❌ 没有切分，有调 prompt 拟合用例的风险 |
| **版本化** | 用例集要像代码一样进 git、可追溯 | ✅ `cases.jsonl` 进了 git |
| **闭环来源** | 线上 bad case 要能回灌 | ✅ 部分：改造 7 已接通「trace 落盘 → 半自动甄别 → 人审回灌」（见 §3），⚠️ 但无真实线上流量，「在线」是模拟 |

### 4.3 一个值得讲的工程细节：加载即校验

> 🔗 [run_evals.py:42-66](../evals/run_evals.py#L42) `load_cases`

本项目读用例时做了两件「数据卫生」的事，面试可当亮点：
1. **坏 JSON 不静默跳过**：解析失败时**报出行号再 re-raise**（[:54](../evals/run_evals.py#L54)），让坏数据立刻可见，而不是悄悄漏测。
2. **标签合法性校验**：`expected_intent` 不在 5 类白名单里直接 `SystemExit(2)`（[:58](../evals/run_evals.py#L58)），防手滑 typo 把用例写废还浑然不觉。

> 💬 **面试怎么说**：「数据集我关注规模、真实分布、标注质量、有没有 held-out 防过拟合，以及能不能把线上 bad case 回灌。我这个项目用例还小、是合成的，这是它当前最大的局限；但加载时做了行号报错和标签白名单校验，保证用例本身不带病。」

## §5 三件事之二 · 指标体系（本项目最有料的一节）

指标 = 把「表现好不好」量化成数字。不同层次用不同指标。

### 5.1 分类 / 抽取类指标

最基础。**准确率（accuracy）** = 答对数 / 总数。更细可看**精确率 / 召回率 / F1**（类别不均衡时准确率会骗人，要看 F1）。

**Precision / Recall 是什么（以"意图分类=预约"为例）**：
- **精确率 Precision**：模型说"是预约"的里面，真的是预约的占多少？——衡量"宁缺毋滥"，抓得准不准。
- **召回率 Recall**：真正是预约的里面，模型抓出来了多少？——衡量"别漏了"，抓得全不全。

这两个指标天然是**拉扯（trade-off）**关系：模型越保守，Precision 升、Recall 掉（漏判变多）；模型越激进（啥都往"预约"上判），Recall 升、Precision 掉（误判变多）。极端案例：把所有样本都判成"预约"，Recall 直接 100%，但 Precision 会很难看——**只看单独一个指标会骗人**。

**F1 是什么、为什么叫这个名字**：F1 是 Precision 和 Recall 的**调和平均数**：

```
F1 = 2 × (Precision × Recall) / (Precision + Recall)
```

用调和平均而不是算术平均，是因为调和平均对"短板"更敏感——Precision=100%、Recall=1% 时，算术平均给出 50.5%（看起来还行），调和平均只有约 2%（如实反映"这模型几乎没用"）。这逼着模型**两头都不能差**才能拿高分，防止用极端策略去"刷"某一个指标。

名字的来历：F1 是更一般的 **Fβ-score** 家族的一个特例，完整公式是 `Fβ = (1+β²)×P×R / (β²×P+R)`，`β` 决定你更看重 Recall 还是 Precision；`β=1` 时两者权重相等，公式化简成上面对称的调和平均，这就是 **F1**（"1" 即 β=1，两者同等重要）。这套记法最早来自信息检索领域，F1 是业界默认最常用的平衡版，所以不加说明提到"F1-score"基本就指它。

> 🔗 本项目 [metrics.py:53-62](../evals/metrics.py#L53) `intent_accuracy`：`actual_intent == expected_intent` 的占比。工具调用正确率（§5.2）同时算了召回率、精确率、F1——只看召回率，agent 乱调一堆多余工具也能刷高分；只看精确率，调得少但保守也能刷高分；F1 逼着它"该调的都调了、且没乱调"才能拿高分。

### 5.2 工具调用正确率（agent 特有）

Agent 评估的核心之一。但「正确」有**三个不同严格度**，面试可层层递进讲：

| 严格度 | 看什么 | 难度 |
|---|---|---|
| 名字集合 | 调了哪些工具（不看顺序、不看参数） | 最松 |
| **参数级** | 工具 + 参数都对（`create_appointment(time=14:00)` 的 time 对不对） | 中 |
| 序列级 | 工具的**调用顺序**也对 | 最严 |

> 🔗 **本项目现状（2026-07-01 核实，三档都做了）**：改造 1（archive `evals-drive-agentloop-real-tools`）让运行器真驱动 AgentLoop、`actual_tools` 出真数，解决了「永远 N/A」；改造 2 又把比对从最松的「名字集合」升到了[metrics.py:tool_call_recall_precision_f1](../evals/metrics.py#L133)（P/R/F1，名字级）+ 参数级 F1（比 `expected_tool_args`）+ 序列正确率 + 完全匹配率——三档严格度**都有对应指标**，`baseline.json` 里能看到 `工具调用-召回率/精确率/F1/参数级F1/序列正确率/完全匹配率` 六项。**门禁只守 F1**（名字级、部分给分、平滑退化），其余五项照常打印但不触发阻断（见 §8）。

> 💬 **面试怎么说**：「工具调用正确性有三档——名字集合、参数级、序列级。我项目里三档都实现了：名字集合用 P/R/F1，还加了参数级 F1 和序列正确率/完全匹配率。门禁只守 F1 这一项，因为其他几个是同一底层行为的更严格切面，守 F1 就够平滑地反映退化，不用同时守六个增加误报。」

### 5.3 槽位抽取完整率 + 一个统计细节：宏平均 vs 微平均

> 🔗 本项目 [metrics.py:88-115](../evals/metrics.py#L88) `slot_completeness`

「槽位」= 从话里抽出的结构化字段（时间、技师、时长…）。完整率 = 期望槽位里被正确填出的比例。

本项目用的是**宏平均（macro-average）**（[:102 注释](../evals/metrics.py#L102)）：**先算每条用例的命中比例，再跨用例求平均**，每条用例**等权**。对比：
- **宏平均**：每条用例权重一样 → 不会被「槽位特别多的那条」带偏。
- **微平均（micro）**：把所有槽位汇总成一个大分母 → 槽位多的用例影响大。

> 💬 **面试怎么说**：「指标聚合要分清宏平均和微平均——我项目槽位用的是宏平均，每条用例等权，避免被槽位多的用例带偏。类别不均衡时这个选择会显著影响结论。」**这是个能立刻显出统计素养的小点。**

### 5.4 ⭐ 最值钱的设计：缺数据显式标 N/A，不伪造分母

> 🔗 本项目 [metrics.py:65-81](../evals/metrics.py#L65)、贯穿四个指标

这是**本项目最该拿出来讲的一处判断力**。四个指标都遵循同一范式：

```python
# metrics.py:72 —— 只把「真正测过这维度」的样本纳入分母
eligible = [r for r in results if r.expected_tools is not None and r.actual_tools is not None]
if not eligible:
    return Metric("工具调用正确率", na=True,           # 显式标 N/A，附原因
                  note="本次运行未捕获实际工具调用（需端到端执行 AgentLoop）")
```

**为什么这是好设计**：假设只跑了分类器、没驱动 loop，`actual_tools` 全空（这正是改造 1 之前的真实情况——当时这条 N/A 路径每次都触发）。
- ❌ 错误做法：把没测的算进分母 → 得出「工具调用正确率 0%」→ **误导人以为工具全调错了**。
- ✅ 本项目做法：显式标 **N/A 并写明原因** → 读者一眼知道「不是 0 分，是这次没测」。

> 🔗 **现状（改造 1 之后）**：`actual_tools` 已不再恒空，这条 N/A 路径今天基本不再触发；同一范式仍在别处生效——比如 `slot_completeness` 只把**标了 `expected_slots` 的用例**纳入分母（大多数早期单轮用例没标），以及某条用例真跑抛异常时 `actual_tools`/`actual_slots` 会是 `None`。设计本身没变，只是「测不到」的具体原因从「压根没驱动 loop」变成了「用例没标注这个维度」或「单次运行失败」。

报告渲染也贯彻了这点——[metrics.py:155-157](../evals/metrics.py#L155) 把 N/A 连同原因一起打出来，不悄悄省略。

> 💬 **面试怎么说**（强烈建议背）：「我最在意指标的诚实性——分母只纳入真正测过的样本，没测的维度显式标 N/A 并写明原因，绝不伪造成 0% 或 100%。因为一个虚假的 0% 会让人以为系统全错，比没有数字更有害。」**这句话能直接把你和「只会跑个准确率」的候选人区分开。**

### 5.5 RAG 评估专题（本项目有 RAG，必讲）

本项目知识查询走的是 **RAG（SQLite + FAISS 向量检索）**——[knowledge.py:18](../harness/tools/knowledge.py#L18) 的 `search_knowledge` 工具薄封装了 [services/knowledge_service.py](../services/knowledge_service.py)，embedding 在 [services/text_embedding.py](../services/text_embedding.py)。RAG 系统的评估**分两段**，面试高频：

**① 检索段（retrieval）**——找回来的文档对不对：
- **召回率 Recall@k**：该找的相关文档，前 k 个里找回了几成。
- **精确率 Precision@k**：找回的前 k 个里，有几成是真相关。
- **MRR（平均倒数排名）**：第一个相关文档排在第几位（越靠前越好）。

**② 生成段（generation）——RAG 三元组**（业界经典，TruLens/Ragas 都用）：

| 指标 | 问的问题 | 防的是 |
|---|---|---|
| **Context Relevance（上下文相关性）** | 检索回来的内容和问题相关吗 | 检索跑偏 |
| **Faithfulness / Groundedness（忠实度）** | 回答是不是**有检索内容支撑**、没瞎编 | **幻觉** |
| **Answer Relevance（答案相关性）** | 回答真的回应了用户的问题吗 | 答非所问 |

> 🔗 **本项目现状**：RAG 系统在（检索 + 生成俱全），但 **`evals/` 完全没有评 RAG 质量**——既没测检索 Recall@k，也没测三元组。这不是遗漏，是**主动暂缓**（改造 5，2026-06-24 决策）：本地 RAG（SQLite+FAISS）后续要整体换成一个独立的外部 RAG 服务，现在评本地实现没有长期价值，等迁移完成后再补。

> 💬 **面试怎么说**：「RAG 要分检索段和生成段评——检索看 Recall@k / MRR，生成看 RAG 三元组：上下文相关性、忠实度（防幻觉）、答案相关性。我项目里有 SQLite+FAISS 的 RAG，但这块评估我主动选择暂缓——因为本地 RAG 后续要换成一个独立的外部服务，现在花力气评一个要被替换掉的实现没有长期价值，等迁移完再补，这也是个判断力取舍。」

### 5.6 成本与延迟

生产必看：**延迟**（用户等多久）、**token / 费用**（一次对话烧多少钱）。

> 🔗 本项目只测了**分类器单次调用的延迟**——[run_evals.py:113-118](../evals/run_evals.py#L113) 用 `time.perf_counter()` 计时，[metrics.py:118-132](../evals/metrics.py#L118) `latency_summary` 汇总 **avg / p50 / max**（注意它给了 p50/max 而不只是均值，这点是对的——延迟要看尾部）。
> ⚠️ 但这是**分类器一次调用**的延迟，不是 agent 全链路延迟；**token / 费用完全没测**。

> 💬 **面试怎么说**：「延迟我会看 p50 和 p99 而不只是均值，因为用户体验由尾部决定。我项目测了延迟的 avg/p50/max，但只是分类器单次调用，agent 全链路延迟和 token 成本还没纳入。」

## §6 三件事之三 · 怎么判对错：客观比对 vs LLM-as-judge

§4 有了标准答案、§5 选好了指标，最后一步是**怎么判一条回答到底对不对**。两类判法：

- **客观比对**：能用 `==` / `set` / 数值比的（意图对不对、调了哪些工具）——本项目大部分指标属于这类。
- **LLM-as-judge（模型当裁判）**：用于**没有唯一标准答案**的主观维度——本项目也已经加了一个（回复质量，见下），只是还没校准。

### 6.1 为什么需要 LLM-as-judge

§1.2 说过：很多输出**没有唯一标准答案**（一句回话是否「礼貌、有帮助、相关」无法用 `==` 判）。这时用**另一个 LLM 当裁判**给回答打分，是业界主流解法。

两种打分方式：
- **Pointwise（逐条打分）**：给单个回答打 1–5 分 / 判合格不合格。
- **Pairwise（两两对比）**：给「回答 A vs 回答 B 哪个好」——**通常比逐条打分更稳**（人和模型都更擅长比较而非绝对评分）。

### 6.2 它的坑（面试加分点）

LLM 裁判**自己也有偏差**，知道这些 = 懂行：
- **位置偏差**：倾向选**靠前**的那个 → 对策：A/B 位置互换跑两次。
- **长度偏差**：倾向选**更长**的回答。
- **自我偏好**：模型倾向给**自己同款模型**的输出打高分。
- **校准**：裁判打的分要**和人工标注对齐**过（抽一批人工标，验证裁判和人一致率），否则裁判本身不可信——这条直接通向 §7。

> 🔗 **本项目现状（2026-07-01 核实）**：改造 4（archive `evals-llm-judge-response-quality`）已接入 LLM-as-judge——[metrics.py:response_quality](../evals/metrics.py#L244)，`--judge` 开启后对最终回复做 **pointwise 二元裁决**（passed/not passed），并配了 [`judge_human_agreement`](../evals/metrics.py#L269)（Cohen's κ）作为**校准机制**。⚠️ 诚实边界（代码注释原话）：**裁判默认「未校准」**——`judge_human_agreement` 这个能力有了，但还没真拿一批人工标注去跑过校准，所以回复质量指标目前**不列入门禁**（§8），报告里也会标注「judge 未校准」。且用的是最简单的 pointwise 二元判合格/不合格，**不是** §6.1 说的 pairwise 对比，也没做位置互换。

> 💬 **面试怎么说**：「对没有唯一答案的回复质量，我用了 LLM-as-judge——pointwise 二元裁决，配了和人工标注对齐的 κ 一致率计算。但目前只是有这个机制、还没真跑校准，所以我诚实地把它标成『未校准』且不让它进 CI 门禁。下一步是真做一次人工标注校准、并升级成 pairwise + 位置互换，这样才敢让它当回归信号。」

# 第三部分 · 让评估本身可信（横切关注点）

## §7 评估的可信度：别拿一个会骗人的数字下结论

前面 §4-§6 产出了指标，但**指标本身得可信**，否则是自欺。这一节横切所有格子，把分散在前面的「可信度」要点收口成一处。

### 7.1 治非确定性（核心）

§1.2 的根本难点：**同输入不同输出**。处理不好，跑分就是「今天 82% 明天 79%」的噪声。

- **多次采样取平均**：每条用例跑 N 次，看平均和**方差**，而不是单次。
- **pass@k**：跑 k 次，只要有一次对就算过（适合代码生成等「能对一次就行」的任务）。
- **置信区间**：20 条用例的 85% 和 200 条的 85% 可信度天差地别——样本小要给出不确定性。
- **`temperature=0` 不等于确定**：能降低随机性，但 provider 侧仍可能微抖，不能当成"锁死"。

### 7.2 另两条可信度防线（已在前文，这里收口）

- **裁判可信**：LLM-judge 要和人工标注校准、警惕三种偏差——详见 §6.2。
- **数据可信**：规模、真实分布、held-out 防过拟合——详见 §4.2。

> 🔗 **本项目现状（2026-07-01 核实）**：改造 3（archive `evals-multisample-variance-ci`）已经把「单次跑分」升级为**多次采样 + 聚合**——`--samples N` 跑 N 次取均值，[metrics.py:aggregate_runs](../evals/metrics.py#L524) 算 **mean ± 95% t 置信区间**。`baseline.json` 就是用 `--samples 3` 生成的稳定参照；门禁默认单次跑 + 20pp 容差（便宜、可频繁跑），容差的取值就是**实测校准**出来的——用当前模型（`deepseek-v4-flash`）观测到的 95% CI 半宽（意图 ±19～22pp、工具 F1 ±6～7pp）反推，不是拍脑袋的魔数（详见 [evals/README.md](../evals/README.md) 门禁小节）。分类器确实设了 `temperature=0`（[run_evals.py](../evals/run_evals.py)）求确定性，但正文也如实指出**`temperature=0` 不等于锁死**——这正是需要 CI 半宽这么大、需要容差机制的原因。

> 💬 **面试怎么说**：「LLM 评估最大的陷阱是拿单次跑分当结论。我项目里已经做了——`--samples N` 多次采样取均值，算 95% t 置信区间；生成基线用 3 次采样的均值当稳定参照，门禁的容差阈值也是拿实测的 CI 半宽反推出来的，不是拍脑袋定的。temperature=0 能降随机但不等于确定，我这个模型实测意图分类的 CI 半宽能到 ±20pp 左右，这也是为什么门禁只拦得住『大幅回归』而不是任意小幅波动。」

# 第四部分 · 让评估发挥作用（落地）

## §8 落地之一 · 回归门禁与 CI

评估的价值不在「跑一次截图」，而在**变成关卡**：新版本不达标就**别想合并/发布**。

要素：
1. **持久化基线**：把上一版的分数存下来。
2. **阈值 / 门禁**：新版本低于基线（或低于绝对阈值）就**让 CI 失败**。
3. **退出码语义**：脚本要用退出码告诉 CI「过 / 没过 / 没真跑」。

> 🔗 本项目锚定（2026-07-01 核实，已从「规划中」升级为「已落地」）：
> - **退出码语义做得不错**——[run_evals.py](../evals/run_evals.py) 用 `0`=正常跑完、`1`=文件缺失、`2`=用例非法/无 key 优雅降级/`--gate` 与 `--update-baseline` 互斥、`3`=**检测到回归**。CI 能据此区分「过 / 没过 / 没真跑」。
> - **优雅降级**：没配 API key 不崩，退而打印用例清单 + 提示，非零退出。
> - **✅ 持久化基线 + 阈值阻断已落地（改造 6，archive `evals-ci-regression-gate`）**：`--update-baseline` 把跑分落盘为 [baseline.json](../evals/baseline.json)；`--gate` 跑完比对基线，被守指标回归（`当前 < 基线 − 容差`）就退出码 `3` 结束；已接进 [phase.md](../.claude/commands/phase.md) 闸门 2（exit 3 阻断归档、2 跳过、1 警告）。门禁**只守正确性子集**：意图分类准确率、工具调用 F1、槽位抽取完整率，刻意排除环境相关的延迟和未校准的 judge 回复质量。
> - ⚠️ **仍未收尾的部分**：改造 8 第二切片（多轮用例）落地后基线已在本地被重定为 35 条集，但按流程要求的「人审批准 + 门禁在新基线上复核仍稳定守 3 项」这两步还没走完（详见 §12、§13）——"CI 门禁已落地"这句话本身是真的，但**当前这一版基线**还没经过完整流程收尾。

> 💬 **面试怎么说**：「评估要接进 CI 当回归门禁才有意义——存基线、设阈值、不达标就让 CI 失败，用退出码区分过/没过/没真跑。我这个项目已经做了：基线持久化、门禁比对、接进开发流程的验证闸门，门禁只守正确性子集、用容差吸收 LLM 的抖动。最近一次数据集扩充（加多轮用例）之后，基线重定和门禁复核这两步的人审收尾还没走完，这是我现在最诚实的一个开放项——基础设施是好的，但每次改数据集都要走完整个流程才能真正信任新基线。」

## §9 落地之二 · 业界工具速览（应对「你用过哪些评估工具」）

面试常问「了解哪些评估框架」。**你不必都用过，但要知道它们各自解决什么问题、怎么选**。下面按定位分类——记定位，别记 API。

| 工具 | 类型 | 一句话定位 | 什么时候选它 |
|---|---|---|---|
| **LangSmith** | 商业（LangChain 家） | 追踪 + 数据集 + 评估一体；和 LangChain 生态无缝 | 已用 LangChain（**本项目正是**），想要 trace + eval 一站式 |
| **LangFuse** | 开源 | LangSmith 的开源平替：可观测 + 评估 + 数据集 | 想自托管、不想锁定商业平台 |
| **Ragas** | 开源 | **专攻 RAG 指标**（忠实度、上下文相关性、答案相关性…） | 评 RAG 质量（**本项目的 RAG 正缺这个**） |
| **DeepEval** | 开源 | 「pytest 风格」的 LLM 评估，断言式、易进 CI | 想把 LLM 评估写得像写单测、接 CI |
| **OpenAI Evals** | 开源 | OpenAI 的评估框架 + 用例注册表 | 偏 OpenAI 生态、想复用社区用例 |
| **Promptfoo** | 开源 | 配置驱动（YAML）批量测 prompt，支持红队/越狱 | 想快速横向对比多 prompt/模型，做安全测试 |
| **Braintrust / TruLens** | 商业 / 开源 | 评估平台 / feedback 函数（TruLens 推广了 RAG 三元组） | 要平台化管理评估、或要现成的 RAG 三元组实现 |

> 🔗 **本项目锚定**：本项目是**自研的轻量评估**（[`evals/`](../evals/) 纯 Python + 纯函数指标），**没用任何上述框架**。但它栈是 **LangChain**（[task_classifier.py:16](../agents/task_classification/task_classifier.py#L16)、[agent_loop.py:18](../harness/runtime/agent_loop.py#L18) 都 import langchain），所以「自然延伸是接 **LangSmith**（同生态）评 trace，接 **Ragas** 评 RAG」。

> 💬 **面试怎么说**（诚实版，重要）：「我项目里是**自研的轻量评估框架**——纯函数算指标、可离线确定性单测。业界常用的我了解定位：LangSmith 是 LangChain 生态的 trace+eval 一体方案、LangFuse 是它的开源平替，Ragas 专做 RAG 指标，DeepEval 把评估写成 pytest 风格方便进 CI。我这个项目栈是 LangChain，所以自然的下一步是接 LangSmith 评 trace、接 Ragas 评 RAG。」**——既不假装用过，又显出你懂选型。**

# 第五部分 · 面试实战

## §10 高频面试问答（背熟）

> 答案都尽量「**概念 + 本项目举例**」，这样既显理论又显落地。

**Q1. 你怎么评估一个 agent 的性能？**
> 分三层：组件级（单个分类器/检索器准不准）、端到端轨迹级（工具调用序列、多轮状态对不对）、系统级（业务指标）。再分离线（防回归）和在线（抓真实问题）两条腿，且要闭环——线上 bad case 回灌离线集。我做过的项目里实现了离线 + 组件级（意图分类）+ 端到端工具调用（参数级/序列级）+ 部分多轮轨迹 + 模拟的在线闭环；真正还没做的是系统级业务指标，以及数据集规模化到能撑住统计意义。

**Q2. LLM 输出不确定，你怎么保证评估可信？**
> 不拿单次跑分当结论：多次采样看均值和**方差**，小样本给置信区间，必要时用 pass@k。temperature=0 能降随机但不等于锁死。我项目里做了——`--samples N` 多次采样、聚合成 mean ± 95% t 置信区间，生成基线用的就是这个稳定均值；门禁的容差阈值也是拿实测的 CI 半宽反推的，不是拍脑袋定的。

**Q3.（陷阱题）那你这个项目的槽位抽取完整率具体是怎么判定的？**
> 老实说它是**存在性口径**，不是精确匹配——只看期望的槽位键（时间、项目、技师…）有没有被抽出来，不比值对不对。这是我实测后妥协的结果：agent 抽出的槽位值是自由文本，`start_time` 这种字段经常把相对时间换算错，逐字精确匹配会几乎恒 miss，反而掩盖了「有没有抽到」这个更基本的问题。所以我把口径明确定成「存在性/覆盖率」，和 `expected_tool_args` 的参数级精确比对分开写清楚，不混为一谈。**（这题以前的诚实点是"工具调用是 N/A"，改造 1 接上 AgentLoop 后已经解决；现在的诚实点变成了槽位口径的这个取舍。）**

**Q4. 没有标准答案的回复质量怎么评？**
> 用 LLM-as-judge。我项目里已经加了一个——pointwise 二元裁决回复合格不合格，还配了和人工标注对齐的 κ 一致率计算函数。但诚实说目前只是有这个**机制**、还没真拿一批人工标注去跑过校准，所以我把它标成「未校准」，也没让它进 CI 门禁。要做严，下一步是真做一次人工校准、并升级成 pairwise 对比 + 位置互换消除位置偏差。

**Q5. RAG 系统怎么评？**
> 分检索段和生成段。检索看 Recall@k、Precision@k、MRR；生成看 RAG 三元组——上下文相关性、忠实度（防幻觉）、答案相关性。我项目有 SQLite+FAISS 的 RAG，但这块评估**主动暂缓**了——因为本地 RAG 后续要整体换成一个独立的外部服务，现在评本地实现的检索/生成质量没有长期价值，等迁移完再补。

**Q6. 评估怎么接进开发流程？**
> 接成 CI 回归门禁：存基线、设阈值、不达标 CI 失败，用退出码区分通过/失败/跳过。我项目这块已经落地了——基线持久化 + 阈值阻断 + 接进开发流程的验证闸门，退出码语义和无 key 优雅降级也都做了。诚实的地方是：每次数据集变了都要走「人审批准重定基线 → 门禁复核仍稳定」这个流程，我最近加多轮用例后基线已经重定，但这两步收尾还没走完，这提醒我基础设施做好了不代表可以绕过流程。

**Q7. 你的评估用例从哪来、够不够？**
> 我项目现在是 35 条，含 6 条多轮对话，覆盖 5 类意图。坦白说规模仍然偏小、绝大多数是手写合成的，也没有切出 held-out 集——这是它当前最大局限。理想做法是从生产 trace 采样 + 人工标注，做几百上千条，并切出 held-out 防过拟合；我项目里在线回灌的机制已经有了（改造 7），只是目前没有真实流量可采。

**Q8. 准确率和 F1 你会选哪个？**
> 看类别均衡。均衡时准确率够用；不均衡时准确率会骗人（全猜多数类也能高分），要看精确率/召回率/F1。聚合还要分宏平均（每条等权）和微平均——我项目槽位用的是宏平均，避免被槽位多的用例带偏。

**Q9. 你用过哪些评估框架？**
> （见 §9 话术——诚实说自研轻量框架 + 了解 LangSmith/LangFuse/Ragas/DeepEval 的定位 + 本项目的自然延伸。）

**Q10. 你评估设计里最得意的一点是什么？**
> 指标的诚实性：分母只纳入真正测过的样本，没测的显式标 N/A 写明原因，绝不伪造 0%/100%；以及把指标算成纯函数、和「跑模型」解耦，所以评估逻辑本身能离线确定性单测。我觉得评估代码本身也得是可信、可测的。

**Q11. 离线评估和在线监控有什么区别？**
> 离线是上线前用固定标注用例防回归；在线是上线后采样真实流量抓问题，多数没有标准答案，要靠 LLM-judge 和用户反馈信号。两者闭环——线上 bad case 回灌离线集。我项目离线有了；在线这条腿的机制也接通了——trace 落盘、半自动甄别失控信号、人审回灌，但诚实说我这个项目没有真实线上流量，所以「在线」目前是拿开发/手动对话模拟的，机制是真的，流量是假的。

**Q12. 你会怎么评估一个 agent 的工具调用？**
> 三个严格度递进：名字集合（调对工具没）、参数级（参数对不对）、序列级（顺序对不对）。我项目三档都做了——名字级用 P/R/F1，还加了参数级 F1、序列正确率、完全匹配率。不过门禁只守 F1 这一项，因为其余几个是同一底层行为的更严格切面，同时守六个只会增加误报，守住 F1 就能平滑反映退化。

## §11 诚实话术：怎么框定本项目不被戳破

转行同学最大的风险是**无意中吹过头**（说「我做了 agent 性能评估系统」），被追问就崩。**把下面这套框定背下来，把劣势变成判断力的展示。**

> ⚠️ **本节话术曾长期停留在改造 1 之前的状态**（说「只评到分类器、工具调用是 N/A」）。改造 1〜8 落地后，那个具体缺口已经不存在了——继续用旧话术反而会露馅（面试官一看代码发现工具调用早就是真数字）。下面是按 2026-07-01 核实的实际代码状态重写的版本；诚实的**内容**变了，诚实的**姿态**没变。

**❌ 别这样说**：「我做了一套完整的 agent 性能评估系统，什么都测了。」
→ 追问「系统级业务指标呢」「RAG 评估呢」就露馅——这两块是真没做（业务指标完全没采集；RAG 评估主动暂缓）。追问「上次加了多轮用例之后，门禁复核完了吗」也会露馅——最新一次数据集变更的人审+门禁复核收尾还没走完。

**✅ 这样说**：
> 「我搭了一个**评估 harness 框架**，核心有两点判断力：一是**指标完整性**——缺数据显式标 N/A、不伪造分母；二是**计算与执行解耦**——指标是纯函数、不触网，所以评估逻辑本身能离线确定性单测。功能上，它现在覆盖了**组件级意图分类 + 端到端工具调用（参数级/序列级 P/R/F1）+ 部分多轮轨迹 + 多次采样置信区间 + CI 回归门禁 + 模拟的在线闭环**——这些都是真跑出来的数字，不是摆设。诚实说还差三块：**系统级业务指标完全没做**；**RAG 评估主动暂缓**，因为本地 RAG 后续要换成外部服务，现在评没有长期价值；**LLM-judge 评回复质量有了机制但还没校准**，所以没让它进门禁。另外最近一次加多轮用例后，基线重定的人审批准和门禁复核这两步收尾还没走完，这是我现在最新鲜的一个开放项。」

**这套话术的三个好处**：
1. **不吹牛也不藏功**：该说做了的（工具调用、门禁、多次采样）就大方说，不因为曾经诚实过就习惯性自我贬低到过时的状态。
2. **显认知**：用「分层」「N/A 不伪造」「解耦可测」「未校准 judge 不进门禁」这几个词，证明你懂的是方法论而非堆功能。
3. **有路线、且路线是活的**：能说清「现在具体差什么」，而不是背一套写死的模板——这本身就说明你在持续跟踪自己项目的真实状态，而不是记了一份答案就不再看代码。

**记住 §1.1 那句话**：面试官考的是判断力。一个能清楚说出「我评到了哪层、还差哪层、为什么这么设计、上次改动后哪一步还没收尾」的转行新人，比一个声称「全做了」却答不上细节、或者背了一套过时话术的人可信得多。

**一句话结论**：**已从「分类器评估」升级为「端到端 agent 评估」并接上回归门禁与在线闭环**——改造 1〜4 落地了工具调用（参数级/序列级）、LLM-judge 回复质量、多次采样置信区间；改造 6 落地了 CI 回归门禁（基线持久化 + 阈值阻断 + 接进闸门 2）；改造 7 落地了在线评估闭环（生产 trace 落盘 → 半自动甄别 → 人审回灌）。**剩下的缺口集中在「持续投入」**：数据集扩充（改造 8 首切片 `evals-stabilize-gate-three` 已让门禁实守项数稳定到 3；第二切片 `evals-multiturn-cases` 加了多轮用例但基线重定/门禁复核尚未走完人审收尾，见上一行 ⚠️；规模化到几百条/held-out 仍待续做）；RAG 评估（改造 5）暂缓待外部 RAG 服务迁移。详见 §13。

## §13 改造路线图：从「分类器评估」→「完整 agent 评估」

下面 8 项改造按**依赖与 ROI 排序**。每项标了：目标 / 改哪里（锚定真实代码）/ 产出 / 工作量（S·M·L）。

> ⚠️ **这些都是代码变更**——按本项目的 OpenSpec SDD 规矩，每项应各走**一个 OpenSpec change**（`/opsx:propose` → 人审 → `/opsx:apply` → 验证 → 归档），不要直接散改源码（见 [../CLAUDE.md](../CLAUDE.md)）。

```
   改造1 接 AgentLoop  ──┬──▶ 改造2 工具调用做严          [✅ 改造1-4 已落地]
   (地基/解锁最多)        └──▶ 改造3 治非确定性
   改造4 LLM-judge ───────────▶ (回复质量, 独立可并行)
   改造1+2 出真数 ────────────▶ 改造6 CI 门禁 [✅ 已落地] ──▶ 改造7 在线闭环 [✅ 已落地]
   改造8 数据集扩充 ──────────▶ (贯穿始终, 持续做)   [✅ 切片1:稳定门禁守3项; ⚠️ 切片2:多轮对话用例(实现+单测绿,基线重定待人审/门禁复核未收尾); 规模化/held-out 续做]
   改造5 RAG 评估 ────────────▶ ⏸️ 暂缓（待外部 RAG 服务迁移）
```

### ⭐ 改造 1 · 让 run_evals 真跑 AgentLoop — ✅ 已落地

- **目标**：把 evals 从「只跑分类器」升级为「真跑端到端」，让 `actual_tools` / `actual_slots` 出真数——**这是把项目从「分类器评估」变成「agent 评估」的关键一步**。
- **怎么做的**（archive `evals-drive-agentloop-real-tools`）：[run_evals.py](../evals/run_evals.py) 除 `classify_task` 外，另外真构造一个 `AgentLoop` 跑到底，从 exporter 沙盒里还原有序工具调用序列，填进 `EvalResult.actual_tools`。
- **⚠️ 一个当初非踩不可的坑**：生产的**主 loop 只含 `delegate` 一个工具**（[chat_handler.py](../api/chat_handler.py)），若直接在主 loop 上挂钩子只会看到 `"delegate"`，看不到 `find_technician` 等真实领域工具（它们在子 Agent 的工具子集里跑）。落地方案是用一个含全量工具的 registry 直接驱动 loop、并把 tracer 透传进子 Agent 的 `delegate` 工具，这样子 Agent 内部的领域工具调用也能被同一份 exporter 采集到。这点是本项目理解「委派式架构下怎么评估」的一个深度点。
- **产出**：`tool_call_correctness` / `slot_completeness` 从「永远 N/A」→ **真实数字**。§12 表里对应两行已转 ✅。
- **工作量**：M（已完成）

### 改造 2 · 工具调用做严（参数级 + 序列级）— ✅ 已落地

- **目标**：从最松的「名字集合」升到「参数对不对、顺序对不对」（见 §5.2 三档）。
- **怎么做的**：`metrics.py` 新增 `tool_call_recall_precision_f1`（名字级 P/R/F1）+ 参数级 F1（比 `expected_tool_args`）+ 序列正确率 + 完全匹配率；`cases.jsonl` 相应补了 `expected_tool_args`。
- **产出**：工具调用指标从「调对了没」升到「调得对不对」，`baseline.json` 里能看到六个子指标；门禁只守其中的 F1（见 §8）。
- **工作量**：S–M（已完成）

### 改造 3 · 治非确定性（多次采样 + 方差/置信区间）— ✅ 已落地

- **目标**：让跑分从「单次噪声」变成「可信结论」（见 §7）。
- **怎么做的**（archive `evals-multisample-variance-ci`）：`run_evals.py` 支持 `--samples N` 对每条用例跑 N 次；`metrics.py` 的 `aggregate_runs` 算 mean ± 95% t 置信区间。生成基线用 `--samples 3` 的均值；门禁默认容差 0.20 就是拿实测的 CI 半宽反推校准出来的，不是拍脑袋定的。
- **产出**：报告能给出「均值 ± 置信区间（n 次）」而非一个孤零零的数。
- **工作量**：M（已完成）

### 改造 4 · 接 LLM-as-judge（评回复质量）— ✅ 已落地（未校准，未进门禁）

- **目标**：评「没有唯一答案」的回复质量（见 §6）。
- **怎么做的**（archive `evals-llm-judge-response-quality`）：`metrics.py` 新增 `response_quality`——`--judge` 开启后对最终回复做 pointwise 二元裁决（passed/not passed）；配了 `judge_human_agreement`（Cohen's κ）作为和人工标注对齐的校准函数。
- **⚠️ 诚实边界**：目前只是**有校准的能力**，还没真拿一批人工标注跑过校准，所以指标标「未校准」、**不列入门禁**（§8）。也还是最简单的 pointwise 二元判定，不是 §6.1 说的 pairwise 对比，没做位置互换消偏。
- **产出**：从「只有客观指标」扩展到「主观质量也能量化」，但可信度上还没到能当回归信号的程度——这是留给下一轮的续做项，不是新缺口。
- **工作量**：L（核心已完成，校准/pairwise 续做）

### 改造 5 · RAG 评估（检索 + 生成）——⏸️ 暂缓

- **现状（2026-06-24 决策）**：**暂缓，不在当前路线内**。本地 RAG（SQLite+FAISS）后续将整体替换为调用一个独立的外部 RAG 服务，现在评本地实现的检索/生成质量没有长期价值；待迁移完成后，再针对新服务补 RAG 评估。
- **目标**：补上 §5.5 的 RAG 评估空白。
- **改哪里**：对检索结果评 **Recall@k / MRR**（需标注「哪些文档才算相关」）；对生成评 **RAG 三元组**（复用改造 4 的 judge）。评估对象届时是外部 RAG 服务，而非 [knowledge_service.py](../services/knowledge_service.py)。
- **产出**：RAG 这条线终于被评上。**依赖改造 4 的 judge**（三元组靠 judge 打分）+ 外部 RAG 服务迁移完成。
- **工作量**：L

### 改造 6 · CI 回归门禁（基线持久化 + 阈值阻断）— ✅ 已落地

- **目标**：让评估从「人工跑人工看」变成「自动拦不达标」（见 §8）。
- **怎么做的**：`--update-baseline` 把跑分落盘为 [baseline.json](../evals/baseline.json)（全部非 N/A 指标快照）；`--gate` 跑完**比对基线**，被守指标回归（`当前 < 基线 − 容差`）就以**退出码 3** 结束；接进 [phase.md](../.claude/commands/phase.md) 闸门 2（exit 3 阻断、2 跳过、1 警告）。比对/序列化全为**纯函数**（[metrics.py](../evals/metrics.py) `compare_to_baseline`），可离线确定性单测（[test_eval_gate.py](../tests/test_eval_gate.py)）。
- **两个判断力点**：① 门禁**只守正确性子集** `{意图, 工具F1, 槽位}`，刻意排除环境相关的延迟与未校准 judge 的回复质量；② 落地之初**槽位采集未接线**，故门禁曾**实守 2 项**，报告如实标注实守项数、不夸大；后续 change `evals-wire-slot-completeness` 把槽位接线（`actual_slots` 从工具调用 args 还原 + 用例标 `expected_slots`），指标采**存在性口径**（只看抽没抽到、不比精确值——实测发现 agent 抽出的槽位值是自由文本且 `start_time` 常算错日期，精确匹配几乎恒 miss）。门禁守 3 项；预约子 Agent 对单轮输入保守、**单条工具触发是强非确定行为**（实测同一最齐全输入跨跑次 1/3～3/3 波动），故 change `evals-stabilize-gate-three`（改造 8 首切片）补 8 条信息齐全的祈使式预约锚点做**数据集冗余**——单条触发率 ~0.27 但 8 条「全不触发」≈ `0.73^8`，使槽位完整率**稳定非 N/A、门禁稳定实守 3 项**（实测多次单跑 `--gate` 均 PASS/3 项）；诚实保留：冗余降低而非消除回落，极端非确定下单跑仍可能罕见回落 2 项，报告如实给当次实守数。靠 `--samples` + 容差进一步吸收。
- **产出**：兑现 [CLAUDE.md](../CLAUDE.md) 里「闸门 2 跑 evals 防回归」的承诺。**依赖改造 1+2 出真数**。
- **工作量**：M

### 改造 7 · 在线评估闭环（trace 采样 → 标注 → 回灌）— ✅ 已落地

- **目标**：把 §3 的「在线」那条腿接起来。
- **怎么做的**（archive `evals-online-eval-loop`）：补上最底层缺失的一环——**生产入口的 `AgentLoop` 此前没接 tracer、压根不产 trace**。
  1. 新增落盘 [`FileSpanExporter`](../harness/observability/file_exporter.py)（span→单行 JSON 进 `evals/traces/`，不得抛）+ [`SamplingSpanExporter`](../harness/observability/sampling_exporter.py)（按整条 trace 留/弃、**错误优先必留**、`sample_rate` 默认 1.0），接进 [chat_handler](../api/chat_handler.py) 主 loop 并透传子 Agent。
  2. [`evals/triage.py`](../evals/triage.py) 半自动甄别：信号判定放 harness 层 [`trace_signals.py`](../harness/observability/trace_signals.py)（`guardrail_exhausted`/`spin_detected`/`tool_failure`/`max_steps_reached`，纯函数、与采样 exporter 同口径），`scan` 产标注草稿、人工填 `expected_*`、`append` 去重回灌 `cases.jsonl`（带 `source=online`）。
  3. **回灌不自动重定基线**：只打印提醒，`baseline.json` 不动（基线变更走人审，不绕过改造 6 门禁）。
- **两个判断力点**：① 信号口径**严格对齐 `AgentLoop` 真实落点**，`[ERROR]` 前缀属遗留 `agents/` 路径、harness loop 不产，故诚实排除、不臆造信号；② **诚实边界**——本项目无真实流量（「生产 trace」=开发/手动对话），且 C-lite 下子 Agent 自开 root span，子 Agent 内部失败会作为「以被委派 task 为 input」的独立候选出现，跨 loop 关联需 correlation id（后续工作）。
- **产出**：离线 + 在线双腿齐全。**依赖改造 6**（有了门禁，回灌才有意义）。
- **工作量**：L

### 改造 8 · 数据集扩充（贯穿始终）

- **目标**：解决 §4 的「用例少、合成、单轮」局限（起点是 20 条单轮；改造 8 至今已推进到 35 条、含 6 条多轮）。
- **首切片 ✅（change `evals-stabilize-gate-three`）**：补 8 条信息齐全的祈使式预约锚点（精确时间+项目+时长+点名技师，各标 `expected_slots`），用**数据集冗余**平摊掉单条工具触发的强非确定性，使「槽位抽取完整率」稳定非 N/A、门禁稳定实守 3 项（兑现 §12 收口）。判断力点：实测确认单条触发不可控（同输入 1/3～3/3），故杠杆是「足量锚点」而非「改写单条求可靠」；纯数据集变更、不碰子 Agent 与 `services`/`harness`（禁改清单）。
- **第二切片 ⚠️ 实现完成、收尾未完（change `evals-multiturn-cases`）**：引入**多轮对话**用例——`cases.jsonl` 新增 `turns`（有序话语列表）形态与单轮 `input` 并存；运行器按轮驱动同一 AgentLoop 累积 history（仅 user/assistant 对，对齐生产 `chat_handler` 窗口）、跨所有轮次还原工具序列与槽位，意图对**首轮**判定；补 6 条多轮用例（追问补全 / 改约 / 先咨询后预约）。代码 + 单测已完成（`uv run pytest` 239 passed / 9 xfailed），把 §2 的「端到端·轨迹/多轮」从 ❌ 抬到 ⚠️ 部分。判断力点：不改 harness（`AgentLoop.run` 已支持传 `history`），杠杆在 evals 层 + 数据集；多轮触发更不稳定，沿用数据集冗余 + `--samples` + 容差。
  ⚠️ **诚实边界（2026-07-01 核实，尚未收尾）**：本切片的 [design.md 迁移计划第 6 步](../openspec/changes/evals-multiturn-cases/design.md) 要求「`pytest` 绿 → **人审批准** → 重定基线 → `--gate --samples 3` 多次确认稳定守 3 项」；当前只完成了第一步，`baseline.json` 已在本地被重定为 35 条集（无人审记录），而门禁复核（[tasks.md](../openspec/changes/evals-multiturn-cases/tasks.md) 5.2/5.3）还没做。新基线相比旧 29 条基线三项被守指标全部下降（意图 85.1%→72.4%、工具 F1 53.8%→47.8%、槽位完整率 100%→84.9%），符合「多轮用例更难、触发更不稳定」的预期方向，但**新基线下门禁是否仍稳定守 3 项，目前是未验证的开放问题**，不应当默认延续旧基线的结论。
- **续做（仍待）**：[cases.jsonl](../evals/cases.jsonl) 规模化到几百条（含多轮）；从真实流量采样（配合改造 7）；切出 **held-out** 集防过拟合。
- **产出**：让所有指标都有统计意义。**不是一次性任务，是持续投入**。
- **工作量**：持续

### 🎯 如果只做一件事

> ⚠️ **本节曾推荐"做改造 1"**——那是改造 1〜8 落地之前的建议，现在改造 1 早已完成（工具调用真评、参数级/序列级都有了）。按 2026-07-01 的实际现状重新给建议：

**先做（小成本、马上能收尾）**：把改造 8 第二切片（`evals-multiturn-cases`）的收尾走完——补上人审批准，`--gate --samples 3` 在新的 35 条基线上多跑几次确认仍稳定守 3 项，再把 [tasks.md](../openspec/changes/evals-multiturn-cases/tasks.md) 5.2/5.3 打勾、走 `/opsx:archive`。理由：代码和单测都已经绿了，这一步纯粹是流程收尾，不做的话现在的门禁结论是「站不住脚」的——基线换了但没经过审批，是当前唯一一个"看起来做完了、其实没收口"的地方。

**然后做（抬高项目定性的下一大块）**：系统级/业务指标（§2 里唯一还是纯 ❌ 的一层）或数据集规模化 + held-out（改造 8 续做）。二选一取决于面试想突出什么——业务指标能让「评估」真正跟"约成了没"挂钩；held-out 能补上"防过拟合"这个数据可信度的硬缺口。

> 💬 **面试怎么说**（"你下一步会怎么改进"）：「短期先把最近一次数据集扩充（加了多轮用例）的收尾走完——人审批准重定基线、门禁在新基线上复核仍然稳定，这是最快能落地的一步，因为代码本身早就绿了。再往后我会优先补系统级业务指标，因为现在从组件级到端到端轨迹都有了，唯独没有『约成了没』这种业务信号，这是评估金字塔里最上面还空着的一层。」

## §14 生产级蓝图（面试素材：「如果要做到生产级，你会怎么做」）

> 这是面试高频题「**你会怎么把它做到生产级**」的标准答案。
> 前提：§13 的功能改造是**必要不充分**条件——功能齐全只是地基。**生产级 = 功能完整（§13）+ 一整层「运维 · 治理 · 规模」**。
> ⚠️ 本项目自我定位学习/面试（[harness-refactor-plan.md:215](harness-refactor-plan.md#L215) 明确"防过度工程"），**不必真建到这一级**；但你要能讲清楚「生产级长什么样、边界在哪」——这本身就是判断力。

### 14.1 一个心智模型：评估系统的成熟度阶梯

```
L0  Demo        "跑一下看着还行"——靠感觉，无用例
L1  离线回归    固定用例 + 指标 + 防回归                  ← 本项目现在在这（§12）
L2  完整功能    轨迹 / judge / RAG / CI 门禁齐全           ← §13 做完到这
L3  生产级      在线持续评估 + 监控告警 + 数据治理 + SLO    ← 本节 §14
```

面试时先定位「我的项目在 L1，§13 做完到 L2」，再讲「L3 要补下面四层」——条理立现。

### 14.2 生产级要补的四个平面（都在 §13 功能之上）

**① 数据平面｜规模化 + 治理**
- 数据集从「手写 35 条」→ **从生产 trace 持续采样 + 标注流水线**（标注工具、多人标注、一致性 κ 系数、黄金集）。
- 数据治理：**版本化、PII 脱敏、分层**（smoke / full / held-out）、数据血缘。
- 🔗 锚点：本项目 [tracer → exporter](../harness/observability/exporter.py) 就是采样的数据源头，地基已在（见 §3）。

**② 评估平面｜可信 + 可扩展**
- **judge 工业化**：与人工标注的**一致率校准**、**漂移监控**（裁判自己会漂）、多 judge 投票、对 judge 调用本身**采样限成本**。
- 非确定性：N 次采样 + 置信区间成为**标配**；报告**分桶**（按意图/难度）而非一个总分。
- 评估系统自身可测、可回滚——**评估代码也是代码**（本项目这点已做对：metrics 纯函数可单测，见 §5）。

**③ 运维平面｜在线 + 监控 + 门禁**
- **在线持续评估**：对生产流量实时打质量/护栏信号，不只离线跑（§3 的"在线"那条腿）。
- **监控告警 + dashboard + SLO**：如「任务成功率 < 阈值」自动告警。
- **回归门禁进 CI/CD pipeline** 自动阻断（§8 的升级版）；canary / A-B 灰度发布；**runbook + on-call**。

**④ 业务平面｜对齐价值**
- 评估指标**对齐业务 KPI**：预约成功率、转化率、人工介入率、NPS——而非只看意图准确率。
- 成本 / 延迟 SLO 与业务权衡。
- 闭环到**产品决策**：A/B 看哪个 prompt/model 真的提升业务，而非只看离线分。

### 14.3 一个关键取舍：自研 vs 平台

到生产级规模，**别再自研**（呼应 §9 那张表）：

> 自研轻量框架适合学习/小项目（**本项目正是**）；到生产级，trace 量、标注量、看板需求都上来了，我会直接上 **LangSmith / LangFuse / Braintrust** 这类平台，而不是自己造轮子——把精力放在「评什么、指标怎么定」上，而不是基础设施。

### 14.4 💬 面试 60 秒答法（"怎么做到生产级"）

> 「我会先用成熟度阶梯定位：我这项目现在在 **L1 离线回归**，§13 那套功能改造做完到 **L2 功能完整**。**生产级 L3 要在功能之上补四层**：数据平面（生产 trace 采样 + 标注流水线 + 治理）、评估平面（judge 校准与漂移监控、多次采样给置信区间）、运维平面（在线持续评估 + 监控告警 + 门禁进 CI/CD + on-call）、业务平面（指标对齐业务 KPI、闭环到 A/B 决策）。到这个规模我会上 LangSmith 这类平台而不是自研。不过我也清楚我这个项目是学习用，做到 L1–L2 就够，**L3 是有真实流量和团队之后才值得投入——知道边界在哪也是判断力**。」

> 最后一句（**知道边界**）很关键：它让你显得**成熟、不盲目堆工程**，恰好呼应项目路线图 §5 "防过度工程" 的取舍。
