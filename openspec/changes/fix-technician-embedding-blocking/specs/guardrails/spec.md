## ADDED Requirements

### Requirement: 多候选向量化 SHALL 异步并发

需要对多个候选文本做向量化的相似度匹配（当前为技师专长匹配）SHALL 走 provider 的原生异步方法，并 SHALL **并发**发起各候选的向量化请求，MUST NOT 串行逐个 `await`。

本需求是「外部调用超时与非阻塞」在具体调用点上的落地锚：那条需求只在抽象层面禁止同步阻塞，没有任何场景绑到实际路径，这正是技师专长匹配能长期违规而无人察觉的原因（`fix-embedding-timeout-blocking` 只修了知识库那条链，技师这条漏了一个多月）。

并发不只是性能优化：串行 `await` 虽然不冻结事件循环，但会把延迟放大到 `N × RTT`，在 N 个候选、每次上限秒级的前提下，单次工具调用可能超过 agent loop 的工具超时而被整体掐断——**功能上等价于失败**。

向量化结果的顺序 MUST 与候选列表顺序严格对应，使相似度排序结果不因并发而改变。

#### Scenario: 候选向量化期间事件循环仍能推进

- **WHEN** 在 `async` 上下文中触发技师专长相似度匹配，且向量化请求长时间不返回
- **THEN** 同时被调度的其他协程 MUST 继续按时推进（心跳不停），MUST NOT 因同步阻塞而全部停摆

#### Scenario: 多候选并发而非串行

- **WHEN** 对 N 个候选执行相似度匹配
- **THEN** 各候选的向量化请求并发发起，整体耗时约为单次请求的量级，MUST NOT 呈 N 倍串行累加

#### Scenario: 并发不改变排序结果

- **WHEN** 给定固定的候选列表与确定性的向量化实现
- **THEN** 返回的候选索引序列与串行实现完全一致（结果顺序按候选下标对应，不按请求完成顺序）

#### Scenario: 挂起的匹配可被取消

- **WHEN** 相似度匹配正在等待向量化结果时其调用被取消（如触发工具超时）
- **THEN** 该调用 MUST 真正终止，MUST NOT 出现"外层已返回、底层请求仍在后台跑完"的线程与连接泄漏
