## Context

`tool_call_recall_precision_f1`（[evals/metrics.py:132](../../../evals/metrics.py)）对 `_tool_eligible` 筛出的用例算 per-case recall/precision/F1，再宏平均。空期望集走 `if expected else 1.0` 拿免费满分。

这个免费满分**本身没错**——负样本测的正是"不该调工具时别乱调"，给满分是对的。错在把它和难例**平均进同一个数**之后，那个数被当成能力指标读。

本变更做的是可见度，不是口径修正：总 F1 一个 bit 都不改。

约束：
- **不得触发重定基线**（「预约域评测冻结」明令禁止，见 [evals/README.md](../../../evals/README.md)）。
- 域无关——第 4 期 oncall 数据集要直接复用（[docs/agent-eval-fieldguide.md](../../../docs/agent-eval-fieldguide.md) 的「机制 ≠ 数据」分界）。

## Goals / Non-Goals

**Goals:**

- 正/负样本的 F1 各自可见，且带**构成占比**。
- 零门禁影响、零基线变更。
- 分档逻辑域无关，oncall 数据集拿来即用。

**Non-Goals:**

- 不改总 F1 的算法、数值或它在门禁里的地位。
- 不改 `cases.jsonl`、不重定 `baseline.json`。
- 不把分档加进 `GATED_METRICS`（见 D2）。
- 不做正样本内部的难度分档（见 D5）。

## Decisions

### D1 切分判据用 `expected_tools` 空/非空，不用 intent 类别

**选它**：`expected_tools == []` → 负样本，非空 → 正样本。

**为什么不按 intent 切**（`pay`/`statistics`/`other` vs `appointment`/`query`）：那两组今天恰好重合，但

1. **intent 是域绑定的**。oncall 没有 `pay`，按 intent 切的代码到第 4 期要重写——而本变更的全部价值就在于第 4 期能直接用。
2. **切在 `expected_tools` 上才对准了病灶**。免费满分的机制入口就是 `if expected else 1.0` 这一行；按它切，等于把"免费满分的那批"精确隔离出来。按 intent 切只是碰巧命中，一旦某个 intent 的用例开始标注工具就会错位。

判据要对着机制切，不是对着标签切。

### D2 分档 MUST NOT 进 `GATED_METRICS`，并用测试钉死

进了会**要求重定基线**（基线里没有这两项，`compare_to_baseline` 会记 `new`，但一旦有人 `--update-baseline` 就写进去、此后开始守），而重定基线是冻结期明令禁止的。

更实质的理由：**分档指标不适合直接当门禁项**。负样本 F1 天然接近 100%、方差极小，守它几乎恒 pass，是个假门禁；正样本 F1 方差大得多，用现有容差守会频繁误报。要守得先重新定容差，那是另一件事。

加 `test_polarity_metrics_are_not_gated` 钉住——没有它，日后有人觉得"既然算出来了不如守上"是很自然的动作。

### D3 呈现形式：挂在总 F1 下方，带 n 与占比

```
  工具调用-F1     56.2%（n=41）
    ├ 正样本      33.5%（n=26，占 63%）
    └ 负样本      100.0%（n=15，占 37%）
```

**占比不能省**。只给两个 F1 值，读者仍然无法判断总数为什么是这个数；给了占比，"总 F1 = 两档按占比加权"就是自明的，不需要任何解释文字。这正是本变更要传达的那件事。

渲染在 `_fmt_metric` 里按指标名特判（与既有的「端到端延迟」特判同一手法），缩进 + 树线，视觉上是**一组三行**而不是"多了两个指标"。

### D4 不给总 F1 加常驻 ⚠ 提示

技术上可以给 `工具调用-F1` 挂个 `note`，每次跑都打一行"该值随构成变化，勿当能力指标"。

**不这么做**：项目原则是「成功静默、只暴露失败」，一条永远存在的警告会被训练成背景噪声——真出问题时那行 ⚠ 也就没人看了。分档三行紧挨着，占比让结论自明，够了。文字解释留在 fieldguide。

### D5 不做正样本内部的难度分档

原始分析里还有第二层构成变化：正样本内部「1 工具易例」从 19% 涨到 48%、「3 工具难例」从 65% 掉到 38%。按这个再分一档确实能看见更多。

**不做，两个理由**：

1. **难度代理量对 oncall 未必成立**。"期望工具数"在预约域约等于难度（1 个 = 问价，3 个 = 完整预约链）；oncall 的工具粒度完全不同——一次 `vlog_query` 可能比三次 `read_source` 难得多。把预约域的代理量固化进域无关的机制里，是把域知识漏进机制层，正是 `domain-packages` 那期在清的东西。
2. **现在做没有数据能验证**。oncall 数据集还不存在，做出来只能在冻结的 51 条上自我验证。

**触发条件**：第 4 期 oncall 数据集建成后，若正样本 F1 的波动无法由正/负构成解释，再谈第二层——届时难度口径应由**域**提供，而不是写死在 `metrics.py` 里。

### D6 单档为空时标 N/A，不记 0

某档一条用例都没有时（如只跑 `--heldout-only` 且该子集恰好全是正样本），该档标 N/A 并注明原因，沿用既有各指标的做法。**记 0 会被读成"这档全错"**，与"没有样本"是完全相反的意思。

## Risks / Trade-offs

- **报告变长，指标从 8 项到 10 项** → 缓解：D3 的缩进呈现让它读起来是一组三行；且两个新项紧跟总 F1，不散落在别处。
- **有人把分档加进门禁** → 缓解：D2 的守护测试 + design 里写明理由。
- **`aggregate_runs` 多采样下新指标的 CI** → 无需特殊处理：它按指标名通吃、非 N/A 才纳入，分档是普通比率指标，自动获得 mean±t-CI。已列入验证项。
- **负样本 F1 恒 ~100% 显得没信息量** → 那恰恰是信息：它证明"总 F1 的这一半几乎不随模型能力变化"。真正要盯的是正样本那一档。

## Migration Plan

无迁移。不改基线文件、不改用例集、不改门禁判定。回滚 = 撤该 change 的提交。

## Open Questions

- 是否该在报告里直接标出"负样本占比较上次基线漂移了 X"？需要基线里存构成，而存构成就等于动基线文件结构——**留到第 4 期与 oncall 基线一起设计**，那时是新建不是修改，成本低得多。
