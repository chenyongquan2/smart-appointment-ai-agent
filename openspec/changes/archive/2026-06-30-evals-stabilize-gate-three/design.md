## Context

门禁守 `GATED_METRICS = {意图分类准确率, 工具调用-F1, 槽位抽取完整率}`。前两项由分类器/工具捕获恒能出值；第三项依赖预约类用例**真触发工具链**——`actual_slots` 从工具调用 args 还原（见 `eval-harness` 需求「槽位采集（actual_slots）从工具调用还原」）。无工具调用 → `actual_slots=None` → 该用例槽位 N/A；若某次跑**所有**带 `expected_slots` 的用例都没触发工具，则 `槽位抽取完整率` 整体 N/A，门禁按 skipped 处理、当次回落到只守 2 项。

根因不在指标算法，而在**触发率**：预约子 Agent 系统提示要求「信息不足时先追问、不臆测下单」（[harness/subagents/appointment.py:36](../../../harness/subagents/appointment.py#L36)）。对信息不全的单轮输入，它倾向**反问澄清**（不调工具）而非办理；只有信息齐全的祈使式输入才会走 `find_technician → check_availability → create_appointment`。当前带 `expected_slots` 的预约用例约 4 条、单条触发率 ~1/3，则「4 条全不触发」≈ (2/3)^4 ≈ 20%，故偶发回落 2 项。

**约束**：CLAUDE.md 禁改 `services/`、`harness/runtime`、子 Agent 编排；本切片定位「数据集扩充」的最小闭环，唯一杠杆是用例本身。

## Goals / Non-Goals

**Goals:**
- 让带 `expected_slots` 的预约用例在单轮下**稳定触发工具链**，使 `槽位抽取完整率` 在常规跑（含 `--samples 3`）下稳定非 N/A。
- 门禁实守项数稳定为 3（意图 + 工具 F1 + 槽位完整率），兑现教材 §12/§13 改造 8 收口。
- 同步文档现状（README 改造 6 节、fieldguide §12/§13）。

**Non-Goals:**
- 不改子 Agent 系统提示 / 编排 / `services/` / `harness/runtime` 业务逻辑。
- 不改 `metrics.py` 的指标算法与「存在性口径」。
- 不**自动**重定 `baseline.json`；基线变更走人审（本切片 apply 时因评估集改变确需重定，已经人审批准后 `--update-baseline --samples 3` 执行——见 Open Questions）。
- 不做规模化扩充到几百条、不引入多轮用例、不切 held-out（属改造 8 后续切片）。
- 不碰 RAG 评估（改造 5 暂缓）。

## Decisions

### 决策 1：靠「足量信息齐全的祈使式用例」做冗余，而非追求单条可靠触发

- **实测发现（apply 阶段诊断，scratchpad 跑真 loop）**：单条用例的触发**强非确定**——同一条最齐全的现有用例（#20）在两轮各 3 次跑中分别得 3/3 与 1/3；现有 #16/#18/#19（信息不全或「有空吗」式查询）稳定 0/3；信息齐全 + **点名具体技师**的祈使句平均触发率约 0.4（个例 0/3～3/3 间波动）。即「补全信息」能把触发率从 ~0 抬到 ~0.4，但**无法把任何单条做到恒触发**。
- **选择**：因此杠杆是**数量冗余**——新增 **8 条**信息齐全的祈使式预约用例（精确时间 + 项目 + 时长 + 性别/偏好 + **点名具体技师** + 明确「就约X/直接帮我订」），各标 `expected_slots`、措辞与槽位键集各异避免同质；**不改写** #16/#18/#19（它们的 `expected_slots` 偶触发即贡献、不触发即 N/A、皆无害，且保留场景多样性）。
- **量化（用实测 p 校准）**：诊断实测新锚点单条触发率 p≈0.27（低于初估 0.4），「某次跑全不触发」≈ (1−p)^K。新增 8 条 + #20 偶触发：**单跑** ≈ 0.73^8 × 0.5 ≈ 4%、**`--samples 3`**（聚合：3 次只要任一非 N/A 即非 N/A）≈ 4%³ ≈ 6e-5。闸门 2（phase.md）跑的是**单跑** `--gate`，故按单跑校准到 8 条把回落压到个位数百分比；残余由 README 诚实边界 + 偶发重跑兜底。实测：5 条阶段时连续 3 个 run 均「至少一条触发」、槽位指标非 N/A。
- **替代**：① 改写单条追求恒触发 —— 实测不可行（单条非确定）；② 改子 Agent 提示让它更激进 —— 违反禁改清单，且改的是业务行为不是评估；③ 把 phase.md 闸门 2 改成 `--gate --samples 3` —— 更稳但每次归档三倍成本，违背 README「门禁默认单跑求便宜」的既定取舍，本切片不动；④ 放宽门禁把槽位移出 GATED —— 倒退，违背改造 6/8 目标。

### 决策 2：保持「存在性口径」与既有标注纪律不变

- **选择**：`expected_slots` 仍只标「整轮应抽到的槽位键集合」、值仅作说明；命中按键存在性判定。新增/改写用例遵循 `cases.jsonl` 头部注释既定格式。
- **理由**：口径变更不在本切片范围；存在性口径已有充分依据（值为自由文本、`start_time` 常算错）。只动数据、不动判法，验证面最小。

### 决策 3：触发率与实守项数靠真跑实测验收，不靠推算

- **选择**：apply 阶段 `uv run python evals/run_evals.py --gate --samples 3` **多跑数次**（建议 ≥3 次独立 invocation），逐次记录报告末行「当次实守项数」，要求稳定为 3；若仍偶发回落，回到决策 1 继续补齐齐全用例直至稳定。
- **理由**：触发是 LLM 非确定行为，唯一可信验收是真跑观测，不能只凭概率推算。

### 决策 4：诚实边界写进 spec 与文档

- **选择**：spec 与 README 都保留「降低而非消除回落概率」的诚实表述；fieldguide §12 速查表把改造 8 该项从「偶回落 2 项」更新为「常规稳定守 3 项（极端非确定下仍可能回落，报告如实标注）」。
- **理由**：与项目一贯的「不伪造、不夸大」原则一致；面试话术也更稳。

## Risks / Trade-offs

- **[改写后某些用例触发率仍不足]** → apply 阶段实测驱动，逐条补齐到稳定；必要时增补更多齐全用例（纯数据，成本低）。
- **[用例同质化（都成了「信息齐全祈使句」）削弱分布真实性]** → 仅对**带 `expected_slots`** 的子集做此策展（保留改约、延长、追问类等其它预约用例不动），维持意图覆盖与场景多样；真实分布扩充留给改造 8 后续切片。
- **[模型升级或换 provider 后触发率漂移致回落]** → 诚实边界已写明非绝对；门禁报告如实给当次实守数 + `--samples` 吸收抖动；真漂移由门禁/复跑暴露。
- **[基线未含槽位项或值过时致门禁 skip]** → 本切片不自动重定基线；若实守 3 项需要新基线，人审后单独 `--update-baseline`，并在 PR 说明。

## Migration Plan

1. 改写/增补 `evals/cases.jsonl` 预约类用例（标 `expected_slots`），遵循文件头注释格式。
2. `uv run pytest` 绿（用例加载/标签校验等单测不破）。
3. `uv run python evals/run_evals.py --gate --samples 3` 真跑数次，记录每次实守项数，确认稳定为 3。
4. 同步 `evals/README.md` 改造 6 节「诚实保留项」与 `docs/agent-eval-fieldguide.md` §12/§13。
5. 如门禁因基线缺槽位项而 skip，人审后 `--update-baseline` 重定基线（单独说明，不在自动流程内）。
- **回滚**：纯数据/文档变更，`git revert` 即可，无运行时副作用。
