# guardrails 规格（delta）

## ADDED Requirements

### Requirement: 外部调用超时与非阻塞

除 LLM 之外的外部 I/O 调用（当前为嵌入/向量化）SHALL 施加可配置的请求超时上限，缺省值 MUST 为秒级量级而非分钟级。超时 MUST 由 HTTP 客户端自身承担，MUST NOT 仅依赖调用处的外层包装（如 `asyncio.wait_for`）。

在 `async` 上下文中 MUST NOT 执行同步阻塞 I/O。此类调用 SHALL 走 provider 的原生异步方法，使其可被取消。

两条约束缺一不可，因为它们防的是**两个不同的缺陷**：

- 只有客户端超时、调用仍是同步的：请求会在上限内返回，但这段时间里**整个事件循环是冻住的**——同进程内所有协程（含 IM 长连接的收包与心跳）一并停摆。
- 只有异步化、没有客户端超时：事件循环能继续推进，但那次调用可能**永不返回**，连接与任务无限期泄漏。

「超时不得只依赖外层包装」是从实测缺陷中反推出的硬约束：`asyncio.wait_for` 只能中断在 await 点让出控制权的协程。若被包裹的调用是同步阻塞的，事件循环连超时定时器的回调都无法执行——外层超时形同不存在，却给人「已经有超时了」的错觉。这与既有需求「LLM 调用超时与重试」互补：那条管的是 LLM，本条管其余外部调用。

超时后 SHALL 由调用方按既有的失败路径降级（如检索失败回灌给模型），MUST 记录可排查的错误日志，MUST NOT 静默返回空结果而不留痕。

#### Scenario: 外部调用有秒级超时上限

- **WHEN** 检查嵌入客户端的构造
- **THEN** 其请求超时已被显式设置为可配置的秒级数值，而非沿用底层客户端的分钟级默认值

#### Scenario: 永不返回的调用被按时掐断

- **WHEN** 嵌入服务的请求永不返回
- **THEN** 该调用在配置的超时内以失败收场，不无限期挂起

#### Scenario: 等待期间事件循环仍可推进

- **WHEN** 一次嵌入调用正在等待响应
- **THEN** 同一事件循环上的其它协程仍按时被调度执行，不被该调用阻塞

#### Scenario: async 上下文不含同步阻塞 I/O

- **WHEN** 审查 `async` 方法中的嵌入调用
- **THEN** 它们调用的是原生异步接口，不存在直接调用同步阻塞版本的情形

#### Scenario: 超时可被离线确定性测试

- **WHEN** 注入一个永不返回的假嵌入实现运行测试
- **THEN** 测试在超时内断言失败行为，不触网、不产生真实等待到分钟级

#### Scenario: 超时留下可排查的记录

- **WHEN** 嵌入调用因超时失败
- **THEN** 记录错误日志且调用方按既有失败路径降级，不静默返回空结果
