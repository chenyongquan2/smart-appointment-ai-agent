## Context

`oncall-evals-bootstrap` 把三处「按 A 域校准的全局常量」收进了 `EvalProfile`，漏了第四处同类的：容差 `0.30`。它的失准方式比 `GATED_METRICS` 更隐蔽——不是少守一项（那至少能从报告的「实守 N 项」看出来），而是**守得太松**，报告里一切正常。

现状是用文档兜的：README 写「本域跑门禁必须显式带 `--tolerance 0.10`」。文档防不住忘记。

## Goals / Non-Goals

**Goals:**
- 容差随域声明，不传 `--tolerance` 即用本域校准值
- 显式传参仍能覆盖（排障、临时放宽）
- 报告里能看出这次用的是哪个容差、来自哪儿

**Non-Goals:**
- 改 `compare_to_baseline` 的比对算法（容差一直是它的入参，只改谁提供这个值）
- 重跑评估或重定基线（容差不参与跑分，只参与跑完后的比对）
- 给容差加「按被守指标分别设置」的能力——当前两域都是单值够用，过度设计

## Decisions

### D1：`--tolerance` 默认值改 `None`，而不是保留 `0.30` 再判「是否等于默认值」

用 `None` 作哨兵，`None` = 未传 → 取域声明。

**替代方案**：保留 `default=0.30`，运行时判 `if args.tolerance == 0.30: 用域声明`。否决——那会让「显式传 `--tolerance 0.30`」和「没传」不可区分，用户明确要求 0.30 时会被悄悄换成域声明值。哨兵法没有这个歧义。

### D2：容差校验只查区间，不查「是否等于某次实测半宽」

`EvalProfile.tolerance` 校验为 `0.0 <= tolerance < 1.0`（比率型指标的容差超过 1.0 等于永不回归）。

「容差必须覆盖实测半宽」这条是**流程约束**，写在 spec 与 README 里由人审保证，代码无从校验——半宽是每次重定基线时的观测量，不是代码里的常量。假装能自动校验它反而会给出虚假的安全感。

`0.0` 放行：它表示「零容忍，任何下降都算回归」，是合法且有意义的严格模式（例如某个零方差指标）。

### D3：容差来源标在门禁报告里

报告加一行 `回归门禁（容差 0.100，来自域 'oncall' 声明）` 或 `（容差 0.050，命令行覆盖）`。

理由：容差不再是命令里看得见的字面量后，「这次判定有多松」就成了隐式信息。判定结论（PASS/FAIL）依赖它，故它必须和结论出现在同一处——否则回溯一次可疑的 PASS 要去翻命令历史。

## Risks / Trade-offs

- **[预约域行为可能被无意改变]** 容差从全局默认变成域声明，若声明值抄错，预约域门禁判定会变松/变紧 → **缓解**：预约域声明 `0.30`（照抄现值），并在 `test_eval_profile.py` 用**写死的字面量**断言（不从被测代码取），与该文件既有的「等价性锚点」测试同一范式。
- **[CI/脚本里已有的 `--tolerance 0.10` 变成冗余]** 不是错误，显式传参仍生效且与域声明同值 → **缓解**：README 同步删掉那条要求；冗余参数无害，不做破坏性清理。

## Migration Plan

1. `EvalProfile` 加 `tolerance` 字段 + 区间校验，两域各自声明。
2. `run_evals.py`：argparse 默认改 `None`，`run_baseline` 参数默认改 `None`，比对前解析（显式值优先，否则取 `domain.eval_profile.tolerance`）。
3. 报告标注容差来源。
4. 补离线单测；`uv run pytest` 全绿。
5. README 删过期提醒、补容差随域声明的说明。

**回滚**：还原 argparse 默认值为 `0.30` 并删除字段即回到现状；无数据迁移、无基线变更。
