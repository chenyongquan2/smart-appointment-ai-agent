## Context

`SpinDetector` 对「同一工具、参数每次不同」的打转完全看不见——真实数据实测**抓到病态 0/3**，`连击=1` 出现在每一步、每一条 trace。这已被两次独立生产观测指向（分支复盘的 5-6 次连调；真实群聊 6h→2d→7d 三连超时白等 3 分钟）。

本 change 的形状由**已在真实数据上做完的规则对比**决定，不是设计推演：

| 规则 | 抓到病态 | 误报正当 | 判定 |
|---|---|---|---|
| 现状（连续整步签名全同 ×3） | 0/3 | 0 | 形状错 |
| B 同名连续 ×3（不看参数） | 3/3 | 3 | 把正当枚举全打死 |
| B' 同名连续 ×4 | 2/3 | 2 | 同上，只是轻一点 |
| C 去掉宽度参数后连续 ×3 | 1/3 | 0 | **最直觉的修法，只有 1/3** |
| **D 同 (工具, 身份参数) 出现 ≥3 步** | **2/3** | **0** | 采用 |

7 条真实 trace 按参数序列语义人工标注：3 病态（query 反复改写 6 步无进展 / term 固定 window 2d→30m→7d 振荡 / term 固定 window 6h→30m→12h 振荡）、3 正当（逐租户枚举 prod→uat→stg→dev / logsql→term 换策略后收窄 / 多意图并行检索）、1 边界。

**为什么 C 只有 1/3**（这是本 change 不是"一行改签名"的原因）：真实 step **一步里常有多个工具调用**——那条坏 trace 的 step2 同时查了 prod/30m 与 uat/2d。「连续整步签名相同」一遇多调用就散，无论签名里含不含宽度参数。**问题在判据形状，不在签名算法。**

实施前已核实的约束：

| 事实 | 出处 | 对设计的约束 |
|---|---|---|
| `Tool` 是 dataclass，已有 `dangerous` / `timeout` 两个声明式字段 | `harness/tools/base.py:56-61` | 新增宽度类参数声明有直接先例，且 roadmap 记着「超时值声明在 `Tool` 上而非运行时全局常量」的同源判据 |
| `detect_bad_signals(spans)` 是纯函数，**只收 span、拿不到 registry** | `harness/observability/trace_signals.py` | 它无从知道哪些参数属宽度类 → 必须在记录时提取 |
| `add_tool_call(span, name, args)` 记的是**完整原始 args** | `harness/observability/tracer.py:118` | 扩展点在这里 |
| `AgentLoop` 持有 `self.registry` | `harness/runtime/agent_loop.py` | 它是唯一同时知道"调了什么"与"该工具怎么声明"的地方 |
| 预约域 evals 是知情放弃的弱网（41 条、只存点估计无 CI） | `domains/appointment/evals/baseline.json` | 行为变更没有网兜 → 本 change 只出信号 |

## Goals / Non-Goals

**Goals:**

- 让「同一工具换参反复调用」这一真实失控模式**在 trace 与 triage 里可见**。
- 把「哪些参数不构成调用身份」这一域知识留在工具声明处，域无关运行时零参数名硬编码。
- 保持候选清单信噪比：三种正当模式 0 误报。

**Non-Goals:**

- **不改 `SpinDetector`、不改 `_signature`、不让循环提前终止。** 人审拍定。理由见 D4。
- **不覆盖「改写漂移」**（同工具反复改写检索键、多步无进展）。规则 D 抓不到它——检索键在变、身份不同。7 条数据里它只有 1 个正样本，硬做规则就是猜。`max_steps` 是它的兜底。
- 不动 `services/`、不改工具行为、不改评分指标、不重定 baseline。
- 不给老 trace 做兼容回填（见 D5）。

## Decisions

### D1：判据用「同身份跨步出现次数」，不用「连续相同」

计数口径：对每个步骤，取其全部 `(工具名, 身份参数)` 组合去重后各计 1；同一组合累计出现的**步骤数** ≥ 阈值即命中。

- **按步骤去重而非按调用计数**：否则同一步内并行调 3 次同一工具就直接顶到阈值，把「多意图并行检索」这种正当模式打成误报。
- **不要求连续**：真实数据里病态模式中间会夹别的工具（`load_reference` 插在 `vlog_query` 之间），要求连续就漏。
- **阈值缺省 3**：真实数据上 3 已能分开两类；调高到 4 会漏掉那条 3 步的真实坏 case。阈值可配以便后续按数据调整。

### D2：身份参数在**记录时**提取，判定侧只读结构

`Tool` 新增宽度类参数声明 → `AgentLoop` 记录 `tool_call` 时查 registry 算出身份参数子集 → `tracer.add_tool_call` 写进 event payload → `detect_bad_signals` 只读该字段。

**为何不让判定侧自己剔**：它是纯函数、拿不到 registry，唯一实现方式是硬编码 `{"window","limit","top_k"}` 白名单——那是把**域内容嵌进域无关机制**，与记忆层那三处已知泄漏（`summary_schema.py` 等）完全同类。已经有三处账没还，不该再添一处。

**这与刚落地的 `error_kind` 提取是同一手法**：结构化信息在记录时提取、判定侧只读结构，而不是让下游去解析/猜。沿用同一套路也便于下一个人理解。

**取工具声明的失败要吞**：`AgentLoop` 查 registry 时工具名可能不存在（模型幻觉工具名），此时退化为「全部参数皆身份」，MUST NOT 抛——埋点不得拖垮主流程（沿用 `end_span` 与 `_extract_error_kind` 的同一取舍）。

### D3：宽度类参数声明在 `Tool` 上，缺省空集

缺省空集 → 未声明的工具行为与引入前完全一致（全部参数计入身份），零迁移负担。

**为何不做成运行时全局参数名集合**：一个工具的宽度旋钮可能是另一个工具的身份维度。举例：`limit` 对 `vlog_query` 是宽度，但若将来有个「取第 N 条」的工具，`limit` 就是身份。全局集合必然误伤——这与 `Tool.timeout` 拒绝全局常量是同一个判据（roadmap 第 1 期原文：主 registry 的 `delegate` 内部跑整个子 loop，全局 60s 会误杀）。

### D4：只出信号，不改护栏——先看得见，再谈拦

命中该信号 **MUST NOT** 使循环终止。理由有三层：

1. **风险不对称**：改护栏会提前终止真实用户的请求，而误杀一次正当枚举意味着同事拿不到日志；只出信号最坏情况是 triage 多一条候选待人审。
2. **没有网兜**：预约域 evals 是知情放弃的弱网（41 条、只存点估计无 CI），行为变更的回归覆盖很弱——这是 roadmap 已明写并接受的代价，不该在此时押上去。
3. **数据还不够**：7 条 trace、3 个病态正样本，够支撑"这个信号看得见"，不够支撑"照此终止是安全的"。攒够真实流量（这类模式多久出现一次、多少是正当枚举）再单独立项谈护栏。

这与 change `fix-trace-triage-blindspots` 是同一套路：那次也是先让机制看得见（超时纳入信号），修完才在真实数据上看清 3 条候选长什么样。

### D5：老 trace 不做兼容回填，如实标注

已落盘的 `tool_call` payload 只有完整 `args`、没有身份参数字段，故该信号对老 trace **不会命中**。

**刻意不加「老 trace 用硬编码宽度参数名回退推断」的分支**——那等于把 D2 拒掉的域知识泄漏以"兼容"的名义请回来，且收益仅限那 6 个文件。

⚠ 由此产生一条必须写清的诚实边界：**规则对比表里的「2/3 命中」是离线复算出来的**（分析脚本用完整 args 加一个显式宽度参数集重放），**不是老 trace 真能报出来**。覆盖自本 change 之后落的新 trace 起生效。

### D6：测试用合成 span 复现真实形状，不搬真实数据

那 7 条 trace 含真实 requestId 与同事原话。trace 目录已 gitignore，但**测试进版本库**——与「回灌 `cases.jsonl` 不得带 `user_id`」同一个道理。故测试构造**合成** span：保留形状（几步、每步几个调用、哪些参数在变），把标识值换成假值。

测试 MUST 覆盖三种正当模式各一条，其中**「逐维度枚举 MUST NOT 命中」是最关键的一条**——那是规则 D 相对 B/B' 的全部价值；它一旦回归，这个信号就退化成噪声源。

## Risks / Trade-offs

- **[信号噪声淹掉 triage]** → 三种正当模式各有一条回归测试钉住；上线后先在真实流量上看命中率与内容，不合理就调阈值（阈值可配正是为此）。
- **[漏掉改写漂移，给人"已覆盖打转"的错觉]** → 写进 proposal/design/tasks 三处非目标，并在信号命名上避免用泛化的 "spin" 字样，免得读成"打转都覆盖了"。
- **[`Tool` 加字段影响既有工具]** → 缺省空集，行为不变；已有 608 条测试兜。
- **[记录时提取增加每步开销]** → 一次 dict 推导 + 一次 registry 查表，与既有 `_extract_error_kind` 同量级，可忽略。
- **[护栏仍然拦不住 → 3 分钟白等还会发生]** → **这是本 change 知情不解决的问题**。它只让这件事可见可计数，为后续护栏改动提供数据。不要在收尾时说成"打转问题解决了"。

## Open Questions

1. **信号名**：`repeated_tool_identity` 偏技术、不易读；`same_action_repeated` 更直白但可能与 `spin_detected` 混淆。倾向前者——与 `spin_detected`（护栏产生的 error 事件）明确区分，避免读者以为护栏拦了。
2. **阈值缺省 3 还是 4**：真实数据上 3 命中 2/3 且 0 误报，4 会漏那条 3 步的真实坏 case。先定 3；攒到更多数据后按误报率复核。
3. **是否顺带把身份参数挂到 span attributes**（便于按身份筛 trace）：倾向不做——attributes 是给人快速筛的索引字段，塞结构化 dict 会让它变重；有需要再说。
