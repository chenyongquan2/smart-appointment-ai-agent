# 设计：退役旧意图分类器

## Context

旧分类器 `agents/task_classification/` 在 harness 重构后退出主服务链路，但仍有三个使用方：注册在路由表的 `api/task.py` 端点、`evals/run_evals.py`（意图准确率，且在 `GATED_METRICS`）、专属测试文件。另发现"端到端延迟"指标实测的是分类器单次调用耗时（[run_evals.py:205](../../../evals/run_evals.py) 注释明示），组件退役后该指标失去来源。

## Goals / Non-Goals

**Goals:**
- 删除旧分类器全部残留（组件/端点/测试）
- 意图准确率指标退役，门禁 3 项 → 2 项，基线重定
- 延迟指标改为真正的端到端口径

**Non-Goals:**
- 不动 `cases.jsonl`（`expected_intent` 标签保留为数据集元数据）
- 不引入"从工具选择反推意图"的替代指标（与工具 name 级指标冗余）
- 不动 harness、services、其余 agents 旧层（其余旧层清理归第 2 期领域包化）

## Decisions

### D1 意图指标退役而非改口径

备选是从"模型选了哪个工具"反推意图继续算准确率。否决理由：harness 架构下"选对工具"与"意图理解正确"是同一件事，工具 name 级 F1 已完整覆盖该信号，反推指标是同一信号算两遍、无增量信息；跨代对照的历史使命已随重构归档完成。

### D2 `expected_intent` 标签保留

数据集构成约束（5 类覆盖、dev 每类 ≥5、held-out 覆盖 ≥3 类）、按类分项分析、用例加载校验都依赖它。退役的只是"跑分类器算准确率"，不是标签本身。加载校验逻辑不变。

### D3 延迟指标改口径为端到端真跑耗时

原口径（分类器单次调用）随组件退役失去来源。改为对每条用例计端到端真跑（驱动 AgentLoop 至最终回复，多轮跨轮累计）的耗时。延迟不在门禁（延迟型仅信息展示），故口径变更无回归判定影响；基线重定后新旧延迟数字不可比，README 注明。

### D4 门禁 2 项 + 容差复核

`GATED_METRICS = {工具调用-F1, 槽位抽取完整率}`。容差沿用 0.20，但重定基线时（`--update-baseline --samples 3`）复核两个被守指标的实测 t-CI 半宽仍被 0.20 覆盖（历史实测工具 F1 ±6~7pp、槽位波动更小，预期无虞；若超出则按实测调）。

### D5 `api/task.py` 端点连根删

实现前 grep `web/templates`、`web/static` 与全仓确认无调用方（预期没有——主聊天走 `/chat`）。若发现调用方则该项转为保留端点并在 proposal 中修订（不静默保留）。

## Risks / Trade-offs

- [重定基线后与旧基线数字不可比] → 基线 JSON 进 git，历史可溯；README 记录本次口径变更（少一指标、延迟改口径）。
- [删除后某隐蔽调用方报错] → 实现首任务先全仓 grep；`uv run pytest` 全绿作为兜底网。
- [容差 0.20 对 2 项门禁可能偏松/偏紧] → 重定时用 `--samples 3` 实测半宽复核，数据说话。

## Migration Plan

单 change 单 PR：删除组件 → evals 改造 → 测试更新全绿 → 重定基线 → `--gate` 验证退出 0。回滚 = revert 该 PR（基线文件同在 PR 内，一并回滚）。
